## 一、问题分析：为什么现有方案不够

### 1.1 象棋AI分析的三重挑战

**挑战一：规则复杂性远超国际象棋**

中国象棋的规则系统比国际象棋复杂得多，存在大量"条件限制型规则"：

| 规则 | 表面描述 | 隐含逻辑 | 工程实现难度 |
|------|----------|----------|-------------|
| 马走日 | 马走日字 | 但日字方向的"马腿"位置有棋子时不能走（蹩马腿） | 需要8方向×蹩腿坐标的偏移表 |
| 象走田 | 象走田字 | 但田字中心有棋子时不能走（堵象眼），且不能过河 | 需要4方向×象眼坐标+过河边界 |
| 炮的双重性 | 炮不吃子时直线走 | 吃子时必须隔一个炮架，移动时不需要 | 需区分"移动扫描"和"吃子扫描"两种模式 |
| 将帅照面 | 将帅不能在同列面对面 | 这意味着**任何棋子离开将帅之间的列**都可能导致违规 | 每步走法都需要检测照面 |
| 九宫限制 | 将/仕只能在九宫内 | 红九宫(7-9行, 3-5列) / 黑九宫(0-2行, 3-5列) | 坐标范围硬约束 |
| 兵卒变化 | 过河前只能前进 | 过河后可左右横走，但永远不能后退 | 需要判断当前行数与河界的关系 |

**这些规则的交叉组合，使得通用LLM几乎不可能仅凭文本理解准确重建棋盘空间关系。**

**挑战二：LLM幻觉的四种致命表现**

我们在预研阶段对GPT-4、GLM-5等主流LLM进行象棋分析测试，发现以下四类幻觉：

| 幻觉类型 | 典型表现 | 危害程度 | 出现频率 |
|----------|----------|----------|----------|
| 位置幻觉 | "红车在5路"（实际在3路） | 致命——所有后续分析基于错误事实 | 高 |
| 关系幻觉 | "黑马无根"（实际有黑炮保护） | 严重——误导战术判断 | 高 |
| 走法幻觉 | "红马可走马三进四"（蹩马腿） | 严重——违反基本规则 | 中 |
| 数值幻觉 | "优势扩大50分"（实际-30分） | 中等——误导局面判断 | 中 |

**关键发现**：这些幻觉的危害在于——**普通学习者无法识别**。当AI自信地告诉你"黑马无根，可以直接吃"，而你发现实际有保护时，你的信任就崩塌了。

**挑战三：现有方案的致命断层**

| 方案 | 事实准确性 | 讲解能力 | 致命缺陷 |
|------|------------|----------|----------|
| 纯引擎（Pikafish/象棋巫师） | ★★★★★ | ★☆☆☆☆ | 只输出`+125 h2e2`，不解释为什么 |
| 纯LLM（GPT-4/GLM-5） | ★★☆☆☆ | ★★★★★ | 表达流畅但编造事实 |
| 引擎+LLM拼接（Chess.com模式） | ★★★☆☆ | ★★★☆☆ | LLM在翻译过程中引入新的幻觉 |
| **本系统（规则引擎+Evidence Map+Agent）** | **★★★★★** | **★★★★☆** | **事实100%准确 + 基于事实的教练讲解** |

### 1.2 核心设计决策

基于以上分析，我们做出三个关键设计决策：

**决策一：用规则脚本而非模型提取特征**

| 对比维度 | 机器学习模型 | 规则脚本（本项目） |
|----------|-------------|-------------------|
| 准确率 | 依赖训练数据分布，存在边界case | **100%精确**（逻辑确定性） |
| 可解释性 | 黑盒，无法解释某个标签为什么被检测 | **白盒**，每个标签绑定棋子坐标 |
| 维护成本 | 需要重新训练，数据标注昂贵 | 修改规则即可，即时生效 |
| 幻觉风险 | 存在（误分类 → 错误标签） | **零风险**（逻辑不会出错） |

象棋规则是**完全确定**的系统——给定棋盘状态，任何战术标签的检测结果都是二元确定的（是/否），不存在模糊地带。这天然适合规则引擎。

**决策二：LLM只负责"表达"，规则引擎负责"事实"**

```
错误架构：FEN → LLM（自行理解棋盘 + 分析 + 输出） → 讲解
                    ↑ 在这里产生幻觉

正确架构：FEN → 规则引擎（100%准确提取事实）
                    ↓
              Evidence Map（结构化事实锚点）
                    ↓
              LLM（仅做基于事实的表达） → 教练讲解
                    ↑ 被 Evidence Map 约束，不能编造
```

**决策三：Agent工具调用替代硬编码管线**

传统方案是"提取全部标签→全部喂给LLM→LLM翻译输出"。这种硬管线无法适应不同问题：用户问"为什么不能走马"和"整体局势如何"需要完全不同的分析策略。

我们的方案：给LLM 14个原子化工具，让LLM**自主决定**先查什么、再查什么。LLM变成真正的Agent——像教练一样先审视全局，发现线索后深入调查，最终给出有因果链条的讲解。

## 二、技术选型详解

### 2.1 前端技术栈

| 技术 | 选型 | 候选方案 | 选择理由 |
|------|------|----------|----------|
| UI框架 | React 18 + TypeScript | Vue 3 / Svelte | 组件生态最成熟，TypeScript类型安全 |
| 构建工具 | Vite | Webpack / Parcel | 极速HMR（<100ms），ESM原生模块 |
| 状态管理 | Zustand | Redux / MobX | 无Provider/无样板代码，适合中等复杂度 |
| 动画 | Framer Motion | GSAP / CSS Animation | React原生物理弹簧模型，声明式API |
| 3D渲染 | WebGL原生 | Three.js / React Three Fiber | Liquid Glass需要自定义管线，框架反而增加开销 |
| 参数调试 | Leva | dat.GUI | React集成好，支持持久化 |

**为什么WebGL不用Three.js**：Liquid Glass效果需要精确控制multi-pass渲染管线（4遍FBO pingpong），自定义fragment shader中涉及折射/色散/菲涅尔物理模型，Three.js的抽象层反而增加复杂度和性能开销。

### 2.2 后端技术栈

| 技术 | 选型 | 选择理由 |
|------|------|----------|
| Web框架 | FastAPI + Uvicorn | 原生async/await + 内置SSE支持（StreamingResponse） |
| 象棋引擎 | Pikafish | Stockfish的中国象棋分支，UCI协议，开源，深度可调 |
| 向量数据库 | ChromaDB | 纯Python本地部署，无需额外启动服务，集成简单 |
| 图数据库 | Neo4j 5.x | 棋谱天然是图结构，Cypher查询表达力强 |
| LLM接口 | OpenAI兼容API | 可切换GLM-5/通义千问/DeepSeek，统一Function Calling协议 |

**为什么不用LangChain**：LangChain的Agent抽象太重，我们需要精确控制工具调用时机、结果解析、Evidence Chain追踪。自研Agent循环（3轮 tool call loop）更轻量、可控。

### 2.3 引擎选型：Pikafish

Pikafish是Stockfish的中国象棋分支，支持标准UCI协议：

| 特性 | 详情 |
|------|------|
| 协议 | UCI（Universal Chess Interface）标准 |
| 深度控制 | `go depth N`，N可配置4-20 |
| MultiPV | `setoption name MultiPV value N`，支持Top-N候选 |
| 评估输出 | centipawn（百分之一兵值）精度 |
| 连接方式 | 子进程 + stdin/stdout管道 + 单例连接池 |

## 四、核心模块实现详解

### 4.1 规则引擎：XiangqiRulesEngine

**位置**：`core/rules/xiangqi_rules.py`（约420行）

**核心设计——双轨走法系统**

这是规则引擎最关键的工程决策。规则引擎维护两套走法生成逻辑：

| 方法 | 功能 | 是否过滤自将 | 用途 |
|------|------|-------------|------|
| `_get_raw_moves(board, row, col)` | 仅基于棋子步法规则 | **否** | 攻击范围计算（判断某格是否被攻击） |
| `get_legal_moves(board, row, col)` | 完整合法走法 | **是** | 面向用户的合法走法列表 |

**为什么需要分离？** 考虑以下场景：

```
黑车(4,5)被红马牵制在将帅之间，不能横走（横走后将帅照面或自将）。

场景A：生成黑车的合法走法 → 黑车不能横走 → get_legal_moves 正确过滤

场景B：判断红帅是否被黑车攻击 → 黑车虽然被牵制不能走，但它的攻击"射线"
仍然存在！如果红帅在黑车的横线上，黑车仍然"威胁"着这条线。

如果用 get_legal_moves 来判断攻击，会错误地认为"黑车不能横走→不威胁横线"，
从而漏掉牵制效果。

所以必须用 _get_raw_moves 判断攻击范围——不考虑自将，只看棋子步法规则。
```

**递归陷阱的解决**

将军检测存在天然递归：判断走法是否合法 → 需要检测走后是否自将 → 需要判断敌方是否攻击己方将 → 需要遍历敌方棋子的走法 → 走法是否合法? → 又要检测自将 → ∞

解决方案：`_is_square_attacked()`内部调用`_get_raw_moves()`（原始走法，不含自将过滤），而非`get_legal_moves()`——**切断递归链**。

```python
@staticmethod
def _is_square_attacked(board, row, col, by_red: bool) -> bool:
    """判断某格是否被指定方攻击——基于Raw Moves，无递归。"""
    for r in range(10):
        for c in range(9):
            piece = board[r][c]
            if piece and XiangqiRulesEngine.is_red(piece) == by_red:
                # 调用 _get_raw_moves 而非 get_legal_moves → 无递归
                if (row, col) in XiangqiRulesEngine._get_raw_moves(board, r, c):
                    return True
    return False
```

**马腿检测：8方向偏移表**

马走日字有8个可能方向，每个方向有一个对应的"蹩马腿"检测坐标：

```python
# (目标行偏移, 目标列偏移, 马腿行偏移, 马腿列偏移)
knight_offsets = [
    (+2, +1, +1, 0),   # 下2右1 → 蹩腿在正下方
    (+2, -1, +1, 0),   # 下2左1 → 蹩腿在正下方
    (-2, +1, -1, 0),   # 上2右1 → 蹩腿在正上方
    (-2, -1, -1, 0),   # 上2左1 → 蹩腿在正上方
    (+1, +2, 0, +1),   # 下1右2 → 蹩腿在正右方
    (+1, -2, 0, -1),   # 下1左2 → 蹩腿在正左方
    (-1, +2, 0, +1),   # 上1右2 → 蹩腿在正右方
    (-1, -2, 0, -1),   # 上1左2 → 蹩腿在正左方
]
```

检测逻辑：先算蹩马腿坐标，如果该坐标有棋子则跳过此方向。

**将帅照面检测**

```python
@staticmethod
def _kings_face_each_other(board) -> bool:
    """检查将帅是否照面（同列无遮挡）。"""
    red_king = XiangqiRulesEngine._find_king(board, True)
    black_king = XiangqiRulesEngine._find_king(board, False)
    if not red_king or not black_king:
        return False
    if red_king[1] != black_king[1]:        # 不同列 → 不照面
        return False
    # 检查两王之间是否有任何棋子
    for r in range(min(red_king[0], black_king[0]) + 1,
                   max(red_king[0], black_king[0])):
        if board[r][red_king[1]]:
            return False  # 有遮挡 → 不照面
    return True  # 同列+无遮挡 = 照面
```

**走法合法性三重验证**

每步走法必须通过三道关卡：

```
Step 1: 棋子步法规则（马走日/车走直/象走田...）
Step 2: 不能吃己方棋子
Step 3: 走后不能自将 + 不能造成将帅照面
    → 通过模拟走棋 + _is_square_attacked 检测
```

### 4.2 战术标签检测器：TacticalDetector

**位置**：`core/rules/tactical_detector.py`

**设计原理**：100%规则硬判定，每个被检测到的标签都绑定具体棋子坐标，置信度二元化（检测到=1.0，未检测到=0.0）。不存在"有点像"的灰色地带。

**45个标签的9大检测层级**：

| 层级 | 标签数 | 代表标签 | 检测原理 |
|------|--------|----------|----------|
| 1. 将杀困毙 | 3 | `is_check`, `is_checkmate`, `is_stalemate` | 合法走法数量为0且被将军→将杀 |
| 2. 捉子 | 3 | `is_attack_unprotected`, `is_mutual_attack` | 攻击范围∩无保护棋子 |
| 3. 闪击抽将 | 3 | `is_discovered_check`, `is_double_attack_with_check` | 移动后暴露己方棋子的攻击线 |
| 4. 牵制串打 | 2 | `is_pinned`, `is_cannon_double_attack` | 移动后暴露己方将帅被攻击 |
| 5. 标准杀法 | 8 | 马后炮、铁门栓、双车错... | 棋子位置组合的精确模式匹配 |
| 6. 子力状态 | 2 | `piece_is_unprotected`, `cannon_has_platform` | 遍历保护链关系 |
| 7. 局面语义 | 10 | `phase_opening`, `has_initiative`, `horse_leg_blocked` | 阶段判断+主动权+特殊状态 |
| 8. 走法质量 | 6 | `move_is_blunder`, `move_gives_check` | 引擎评估差值+标签前后变化 |
| 9. 战略评估 | 5 + 3 | `controls_open_file`, `engine_best_by_margin` | 线路控制+引擎数据 |

**标准杀法检测（8种）的实现原理**：

以**马后炮**为例——需要满足三个条件同时成立：
1. 有一方的炮正在将军（攻击线上隔一个子打到敌方将）
2. 那个"炮架"恰好是己方的马
3. 马和将在同一条直线上

以**铁门栓**为例：
1. 在将的所在列或行上，有车或兵控制将门
2. 将的移动走法数为0或极少
3. 必须确认将无法离开受控区域

每种杀法都是精确的棋子位置几何组合判定，不使用任何机器学习。

### 4.3 张力检测器：TensionDetector

**位置**：`core/rules/tension_detector.py`

**设计原理**：张力是"局面中的矛盾和异常"，它驱动AI应该深入分析什么方向。没有张力的局面平淡无奇；高张力的局面意味着即将发生关键变化。

**6种张力类型**：

| 张力 | 英文标识 | 触发条件 | 分析价值 | 优先级 |
|------|----------|----------|----------|--------|
| 评估异常 | `hidden_imbalance` | 引擎评分>300但战术标签<2个 | 引擎与标签产生矛盾——可能存在深层战术标签未覆盖的隐藏优势 | HIGH |
| 子力vs攻势 | `material_vs_initiative` | 子力占优方反而没有攻势标签 | 子多但被动，可能需要主动求战 | HIGH |
| 危机资源 | `crisis_with_resources` | 被将军同时有无根子和隐藏资源 | 危中有机——可能存在弃子反杀 | CRITICAL |
| 沉睡棋子 | `sleeping_piece` | 高价值棋子（车/马/炮）位置不活跃 | 出子效率问题 | MEDIUM |
| 标签矛盾 | `tag_contradiction` | 多个互斥标签同时出现 | 局面复杂度高 | MEDIUM |
| 阶段错位 | `phase_mismatch` | 子力数量与阶段判断不一致 | 判断逻辑可能需要修正 | LOW |

每种张力还附带`suggested_tools`字段，告诉专家应该用哪些工具深入调查。

### 4.4 Agent工具集：14个原子化工具

**位置**：`core/llm/agent_tools.py`

**设计原则**：
- **原子化**：每个工具只做一件事
- **可组合**：复杂分析通过组合多个工具实现
- **结构化返回**：统一`ToolResult(success, data, message, thinking_hint)`
- **candidate_id协议**：走法分析工具只接受规则引擎生成的candidate_id，禁止LLM自行编造UCI走法

**14个工具分类详表**：

**第一类：棋子关系查询（4个）**

| 工具 | 签名 | 返回 | LLM调用场景 |
|------|------|------|------------|
| `get_piece_attacks` | `(fen, piece)` | 攻击范围+攻击到的棋子及其价值 | "这个车能打到哪些子？" |
| `get_piece_defenders` | `(fen, piece)` | 保护者列表+保护数 | "这个马有没有根？"→ 必须调用验证 |
| `get_threats_to_piece` | `(fen, piece)` | 威胁者列表+危险等级 | "哪些子在威胁这个炮？" |
| `get_piece_relations` | `(fen, piece)` | 综合攻防关系矩阵 | "给我这个棋子的全部关系" |

**第二类：走法分析（5个）**

| 工具 | 签名 | 返回 | LLM调用场景 |
|------|------|------|------------|
| `get_move_candidates` | `(fen, limit=12)` | 合法走法列表+candidate_id | 分析前必须先调用，获取走法清单 |
| `analyze_move` | `(fen, candidate_id)` | 走法后果+评分变化+标签变化 | "这步棋走了之后局面怎么变？" |
| `compare_moves` | `(fen, candidate_ids)` | 多走法引擎评分对比排序 | "这三步棋哪个最好？" |
| `get_forcing_sequence` | `(fen, move, depth=3)` | 强制序列变例（将军-应将链） | "走这步之后有没有连续将？" |
| `simulate_move` | `(fen, candidate_id)` | 新局面FEN+关键变化 | "把这步走出来看看状态" |

**第三类：引擎深度分析（2个）**

| 工具 | 签名 | 返回 | LLM调用场景 |
|------|------|------|------------|
| `engine_deep_analysis` | `(fen, depth=20)` | 评分+最佳走法+主变化 | 需要权威评估 |
| `engine_alternatives` | `(fen, top=3)` | Top-N候选走法+分差 | 对比多个候选 |

**第四类：知识检索（3个）**

| 工具 | 签名 | 返回 | LLM调用场景 |
|------|------|------|------------|
| `analyze_position_strategy` | `(fen)` | 阶段+主动权+关键特征 | 宏观战略判断 |
| `query_chess_principles` | `(fen, tension_type)` | 按张力类型匹配棋理原则 | 需要理论支持 |
| `search_chess_knowledge` | `(query, top_k=5)` | RAG语义检索结果+相似度 | 搜索棋书知识 |

**candidate_id协议的重要性**

LLM天然倾向于自行编造走法（如"h2e2"），但这些走法可能不合法。我们的做法是：
1. `get_move_candidates()`返回带candidate_id的合法走法列表
2. 所有走法分析工具（`analyze_move`/`compare_moves`/`simulate_move`）只接受candidate_id
3. LLM**不能绕过规则引擎自行编造UCI走法**

这从协议层面杜绝了LLM走法幻觉。

### 4.5 多专家并行架构

**位置**：`core/llm/multi_agent_orchestrator.py`

**三位专家的角色定义**：

| 专家 | 视角 | 分析重点 | 必填章节 |
|------|------|----------|----------|
| **战术专家**(TacticsExpert) | 微观——棋子攻防 | 捉子/牵制/闪击/杀法/被迫应着 | 【对手处境】必填 |

| **引擎专家**(EngineExpert) | 数据——精确评估 | 评分解读/候选对比/分数落差/强制序列 | 【候选分析】必填 |

**自适应调度决策**：

```python
# core/llm/analysis_policy.py — 9种调度路径
if force_full_team:
    → ["tactics", "strategy", "engine"]     # 强制全团队
elif 问题含引擎关键词:

else:
    → ["tactics", "strategy"]               # 默认双专家
```

- 前端仍展示完整的"战略专家→引擎专家→协调者综合"演出层，保持视觉一致性

### 4.6 Claim证据裁决机制

**位置**：`core/llm/claim.py`

**核心数据结构**：

```python
@dataclass
class EvidenceItem:
    tool_name: str         # 工具名称
    arguments: dict        # 工具参数
    result_summary: str    # 结果摘要
    success: bool = True

@dataclass
class Claim:
    statement: str         # 断言内容（如"红车控制第五路开放线"）
    source: str            # tool_verified / reasoning / unverified
    confidence: str        # high / medium / low
    evidence: List[EvidenceItem]  # 支持该断言的证据链
```

**来源推断逻辑**：

| 条件 | 来源分类 | 权重 |
|------|----------|------|
| 证据文本中包含工具名（如`get_piece_attacks`） | `tool_verified` | 1.0 |
| 含"推理/分析/判断"字样但无工具证据 | `reasoning` | 0.7 |
| 无任何证据支持 | `unverified` | 0.3 |

**合成器裁决规则**：
1. **采纳**：工具验证的Claim直接采纳
2. **标注**：推理型Claim标注来源后采纳
3. **降权**：未验证Claim降权处理
4. **冲突处理**：当两个高权重Claim矛盾时，必须明确解释分歧原因

**解析策略（两层回退）**：
1. **显式标记**：解析`[CLAIM]...[EVIDENCE]...[CONFIDENCE]`结构化标记
2. **隐式回退**：从`【战术发现】`/`【战略评估】`等节标题自动提取

### 4.7 可靠性保障：ReliableLLMClient

**位置**：`core/llm/reliable_client.py`

**三层保护机制**：

| 层级 | 机制 | 参数 | 作用 |
|------|------|------|------|
| 1 | **并发信号量** | `BoundedSemaphore(4)` | 防止瞬时LLM API过载 |
| 2 | **熔断器** | 连续失败≥12次→熔断打开 | 避免雪崩式调用 |
| 3 | **指数退避重试** | `base=1.0s × 2^attempt`，最多2次 | 处理429/5xx瞬时故障 |

**降级策略**：

| 故障场景 | 降级方案 |
|----------|----------|
| 单专家超时/失败 | 其他专家继续执行，合成器自动忽略失败专家 |
| LLM全面不可用 | 熔断器打开，返回纯规则层结构化结果 |
| 引擎进程死亡 | 自动检测+重建进程+重试 |
| 合成器空输出 | 保底综合讲解（基于专家Claim结构化拼接） |

### 4.8 SSE流式输出实现

**后端管线**（`api/main.py`）：

```python
async def deep_stream_endpoint(fen, question, ...):
    async def generate():
        # Step 1: 立即返回初始事件（<10ms）
        yield sse_event({"type": "thinking", "message": "启动分析..."})

        # Step 2: 后台线程执行预计算
        event_queue = queue.Queue()
        def run_precompute():
            evidence_map = TacticalDetector().detect_static(fen).to_evidence_map()
            engine_result = EnginePool.get_pool().analyze(fen, depth=15)
            tensions = TensionDetector().detect(evidence_map, engine_result)
            # 结果放入共享数据结构

        threading.Thread(target=run_precompute).start()

        # Step 3: 后台线程运行多专家
        def run_agents():
            orchestrator = MultiAgentOrchestrator(...)
            orchestrator.analyze(on_event=lambda e: event_queue.put(e))
            event_queue.put({"type": "DONE"})

        threading.Thread(target=run_agents).start()

        # Step 4: 事件循环消费
        while True:
            try:
                event = event_queue.get(timeout=0.5)
                if event["type"] == "DONE":
                    break
                yield sse_event(event)
            except queue.Empty:
                yield sse_event({"type": "heartbeat"})  # 保持连接

        # Step 5: 最终结果
        yield sse_event({"type": "result", "explanation": final_text})

    return StreamingResponse(generate(), media_type="text/event-stream",
                            headers={"Cache-Control": "no-cache",
                                     "X-Accel-Buffering": "no"})
```

**前端SSE消费**（`frontend/src/App.tsx`）：

```

### 5.1 Liquid Glass WebGL渲染管线

**4遍渲染管线（Multi-Pass FBO Pingpong）**：

```
Pass 1: 背景采样
    背景canvas → FBO[0]（SDF圆角矩形 + 阴影）
    Fragment Shader: fragment-bg.glsl
    关键技术: Superellipse SDF (u_shapeRoundness=2-7)

Pass 2: 垂直高斯模糊
    FBO[0] → FBO[1]
    Fragment Shader: fragment-vblur.glsl
    最大采样: 201个（u_blurRadius=0-200）

Pass 3: 水平高斯模糊
    FBO[1] → FBO[2]（折射用模糊背景完成）
    Fragment Shader: fragment-hblur.glsl

Pass 4: 折射合成（最终输出到屏幕）
    FBO[2] + 原始背景 → Screen
    Fragment Shader: fragment-main.glsl
    物理效果:
      - 折射: u_refFactor(1.0-4.0) IOR偏移采样模糊背景
      - 色散: u_refDispersion(0-50) RGB三通道不同偏移
      - 菲涅尔: pow(edge_factor, 5.0) 边缘反射
      - 炫光: u_glareFactor(0-120) + u_glareAngle(-180°-180°)

## 六、安全与可靠性设计

### 6.1 LLM调用保护矩阵

| 保护机制 | 实现方式 | 参数 | 触发场景 |
|----------|----------|------|----------|
| 并发限制 | `BoundedSemaphore` | 默认4路 | 防止瞬时API过载 |
| 熔断器 | 连续失败计数器 | ≥12次打开 | 避免雪崩式调用 |
| 指数退避 | `base × 2^attempt` | base=1.0s, 最多2次 | 处理429/5xx |
| 超时控制 | 请求级超时 | 120秒 | 防止无限等待 |
| 工具超时 | 单工具超时 | 45秒 | 防止单工具阻塞 |

### 6.2 降级策略

| 故障层级 | 降级方案 | 用户感知 |
|----------|----------|----------|
| 单专家失败 | 其余专家继续，合成器标注缺失维度 | 分析角度减少但仍可用 |
| LLM全面超时 | 切换单专家快速分析 | 响应变快但深度降低 |
| 引擎不可用 | 纯标签基础评估 | 无评分但有战术分析 |
| 引擎进程死亡 | 自动检测+重建进程+重试 | 用户无感知 |
| 合成器空输出 | 保底结构化拼接 | 文本质量下降但内容完整 |
| 全部失败 | 返回纯规则层Evidence Map | 显示结构化标签和张力 |
