## 二、难点一：象棋规则精确实现与递归陷阱

### 2.1 问题本质

中国象棋规则系统比国际象棋复杂得多——不仅每种棋子有独特的移动限制（马腿、象眼、九宫、过河），更存在一个**工程上的递归陷阱**：规则引擎的核心功能之间形成循环依赖。

**规则复杂度对比**：

| 规则维度 | 国际象棋 | 中国象棋 | 额外工程量 |
|----------|----------|----------|-----------|
| 马的走法 | 日字跳，无限制 | 日字跳+蹩马腿检测 | 8方向×蹩腿坐标偏移表 |
| 象的走法 | 斜线无限 | 田字+象眼检测+不过河 | 4方向×象眼坐标+河界边界 |
| 炮的走法 | 不存在 | 移动直线走，吃子需炮架 | 双模式扫描（移动/吃子） |
| 王的限制 | 全棋盘 | 九宫内+将帅照面禁令 | 九宫坐标约束+照面检测 |
| 兵的变化 | 固定方向 | 过河前只进，过河后可横 | 行号与河界的动态判断 |
| 规则交叉 | 简单 | **任何走法都可能触发照面/自将** | 每步走法的三重验证 |

### 2.2 核心难点：递归陷阱

**问题描述**：

规则引擎需要以下两个核心功能，它们之间存在循环依赖：

```
get_legal_moves(piece) — 获取某棋子的合法走法
    需要调用 → _is_in_check(board_after_move) — 走后是否自将
        需要调用 → _is_square_attacked(king_pos) — 帅位是否被攻击
            需要调用 → 遍历所有敌方棋子的走法 — 看谁能打到帅
                需要调用 → get_legal_moves(enemy_piece) — 敌方棋子的合法走法
                    需要调用 → _is_in_check(...) — ∞ 无限递归！
```

**如果不解决这个递归，规则引擎根本无法工作。**

### 2.3 解决方案：双轨走法系统

**核心洞察**："攻击范围"和"合法走法"是不同的概念。

```
合法走法 = 棋子步法规则 - 自将走法 - 照面走法
攻击范围 = 仅棋子步法规则（不管自将不自将）
```

**关键区别的具体场景**：

```
局面：黑车(4,5)在红帅和黑将之间，被牵制

情况A — 生成黑车的合法走法：
  黑车想横走(4,3) → 模拟走棋 → 黑将被红车直接攻击 → 自将！→ 不合法
  结论：黑车此时不能横走

情况B — 判断红帅(9,5)是否被黑车攻击：
  如果用"合法走法"判断：黑车不能横走 → 不在攻击范围 → 红帅安全？
  错！黑车虽然被牵制不能走，但它的"攻击射线"仍然覆盖横线。
  如果黑车离开，牵制效果就消失了——这恰恰是牵制的定义。

  正确做法：用"原始走法"（raw moves）判断攻击范围 → 黑车横线仍在攻击范围
```

**实现**：

```python
# _get_raw_moves: 仅基于棋子步法规则，不过滤自将 → 用于攻击检测
@staticmethod
def _get_raw_moves(board, row, col) -> List[Tuple[int, int]]:
    piece = board[row][col]
    piece_type = piece.lower()
    if piece_type == 'n':
        return XiangqiRulesEngine._knight_moves(board, row, col, is_red)
    # ... 各棋子步法 ...

# _is_square_attacked: 基于 _get_raw_moves → 无递归！
@staticmethod
def _is_square_attacked(board, row, col, by_red) -> bool:
    for r in range(10):
        for c in range(9):
            piece = board[r][c]
            if piece and is_red(piece) == by_red:
                if (row, col) in _get_raw_moves(board, r, c):  # 不触发get_legal_moves
                    return True
    return False

# get_legal_moves: 生成合法走法 → 调用 _is_square_attacked（基于raw moves）
@staticmethod
def get_legal_moves(board, row, col) -> List[Tuple[int, int]]:
    raw = _get_raw_moves(board, row, col)
    legal = []
    for nr, nc in raw:
        if _is_valid_move(board, row, col, nr, nc, is_red):  # 内部调用_is_square_attacked
            legal.append((nr, nc))
    return legal
```

**递归链被切断**：`get_legal_moves` → `_is_valid_move` → `_is_square_attacked` → `_get_raw_moves`（终止，不再调用`get_legal_moves`）。

### 2.4 马腿检测：8方向三维偏移表

马走日字有8个方向，每个方向有明确的"蹩马腿"位置：

```
马在(5,5)的8个方向：

方向  目标位置    蹩腿位置    蹩腿语义
+2,+1  (7,6)    (6,5)      正下方有子→不能跳
+2,-1  (7,4)    (6,5)      正下方有子→不能跳
-2,+1  (3,6)    (4,5)      正上方有子→不能跳
-2,-1  (3,4)    (4,5)      正上方有子→不能跳
+1,+2  (6,7)    (5,6)      正右方有子→不能跳
+1,-2  (6,3)    (5,4)      正左方有子→不能跳
-1,+2  (4,7)    (5,6)      正右方有子→不能跳
-1,-2  (4,3)    (5,4)      正左方有子→不能跳
```

用四元组`(dr, dc, block_r, block_c)`编码：
```python
knight_offsets = [
    (+2, +1, +1, 0),  (+2, -1, +1, 0),
    (-2, +1, -1, 0),  (-2, -1, -1, 0),
    (+1, +2, 0, +1),  (+1, -2, 0, -1),
    (-1, +2, 0, +1),  (-1, -2, 0, -1),
]
# 检测: if board[row+block_r][col+block_c] 有棋子 → 此方向被蹩腿
```

### 2.5 将帅照面检测

将帅照面是中国象棋独有规则：双方将帅在同一列，中间无任何棋子遮挡时，形成违规。

```python
@staticmethod
def _kings_face_each_other(board) -> bool:
    red_king = _find_king(board, True)    # 红帅位置
    black_king = _find_king(board, False)  # 黑将位置
    if red_king[1] != black_king[1]:       # 不同列 → 不可能照面
        return False
    # 检查两王之间的每一格
    for r in range(min_row + 1, max_row):
        if board[r][red_king[1]]:          # 有子遮挡 → 不照面
            return False
    return True  # 同列+无遮挡 = 照面违规
```

**工程影响**：每步走法验证时，都必须模拟走棋后调用此函数检测，任何导致照面的走法都是非法的。这包括：移走遮挡子、将帅移到同列等间接情况。

## 三、难点二：LLM幻觉的架构级防护

### 3.1 问题本质

LLM幻觉不是"偶尔出错"，而是一个**系统性问题**——通用LLM从未真正"理解"棋盘空间，它只是基于文本统计模式拼接出看似合理的分析。

**我们在预研阶段发现的四类幻觉**：

| 幻觉类型 | 真实案例 | 原因分析 |
|----------|----------|----------|
| **位置幻觉** | LLM说"红车在第5列"，实际在第3列 | LLM无法从FEN字符串准确重建10×9空间 |
| **关系幻觉** | LLM说"黑马无根"，实际有黑炮保护 | LLM不执行攻击范围计算，凭直觉猜测 |
| **走法幻觉** | LLM推荐蹩马腿的走法 | LLM不知道马腿位置有棋子 |
| **数值幻觉** | LLM说"优势+50分"，引擎评-30分 | LLM编造数字来支持自己的叙述 |

**核心洞察**：这些幻觉无法通过Prompt Engineering解决——因为问题不在于LLM的"态度"，而在于LLM**根本不具备精确的空间计算能力**。必须从架构层面解决。

### 3.2 解决方案：三层Evidence Map约束架构

**第一层：规则引擎100%精确提取事实**

规则引擎分析FEN，输出带坐标绑定的结构化Evidence Map：

```python
# TacticalDetector.detect_static(fen) → FullDetectionResult
# 转换为 Evidence Map:
{
    "facts_rules": [
        {
            "tag": "is_attack_unprotected",
            "confidence": 1.0,
            "bind_pieces": ["红车-(5,8)", "黑马-(7,8)"],  # 精确坐标绑定
            "description": "红方有无保护棋子被攻击",
            "source": "static"
        },
        {
            "tag": "is_pinned",
            "confidence": 1.0,
            "bind_pieces": ["黑车-(4,5)"],
            "description": "有棋子被牵制，移动后将暴露将帅",
            "source": "static"
        }
        // ... 45个标签的检测结果
    ],
    "evidence_source": { "rules": "TACTICAL_DETECTOR" }
}
```

**关键设计**：每个标签都绑定相关棋子的精确坐标。不是"有棋子被牵制"，而是"黑车-(4,5)被牵制"——坐标是不可篡改的。

**第二层：System Prompt硬约束LLM行为边界**

```
以下内容只能来自 Evidence Map 或工具返回，绝对不能凭感觉填写：
- 任何具体棋子的坐标或位置
- 任何走法的具体效果
- 任何引擎评估数值

关于"保护"关系的硬规则：
如果你提到"保护"，必须调用 get_piece_defenders 验证。
绝对不能在未调用工具验证的情况下说"XX保护了YY"。
```

**第三层：工具调用实时验证**

当LLM需要做出超越Evidence Map范围的判断时，必须调用工具验证：

```
场景：LLM想说"红车威胁黑马，黑马无根"

Step 1: LLM调用 get_piece_defenders(fen, "黑马")
Step 2: 工具返回: {"defender_count": 1, "defenders": [{"piece": "黑炮", "pos": "(2,8)"}]}
Step 3: LLM修正输出: "红车威胁黑马，但黑马有黑炮-(2,8)保护"

如果LLM跳过工具调用直接说"黑马无根" → 这就是幻觉。
三层约束确保LLM不会走到这一步。
```

### 3.3 保护关系验证——一个经典错误的深入分析

"保护关系"是LLM最容易产生幻觉的领域。原因：

**错误做法（产生幻觉）**：
```
LLM的推理链: "红炮在第5列，黑马也在第5列，
所以红炮可以直接打到黑马，黑马无根。"

真相: 红炮和黑马之间还有一个棋子（炮架），
红炮是隔子吃，不是直打。而且黑马有黑车在同行保护。
```

**正确做法（工具验证）**：
```python
# get_piece_defenders 的实现原理
def get_piece_defenders(self, fen, piece) -> ToolResult:
    target_pos = self._parse_piece_position(piece)
    board = self._parse_fen(fen)
    is_red = self._is_red(board[target_pos])
    
    defenders = []
    for r in range(10):
        for c in range(9):
            p = board[r][c]
            # 只看同方棋子
            if p and self._is_red(p) == is_red and (r,c) != target_pos:
                # 关键：用 _get_raw_moves 计算攻击范围
                attacks = XiangqiRulesEngine._get_raw_moves(board, r, c)
                if target_pos in attacks:
                    defenders.append({"piece": p, "pos": (r,c)})
    
    return ToolResult(success=True, data={
        "defender_count": len(defenders),
        "defenders": defenders
    })
```

**工程关键**：`get_piece_defenders`使用`_get_raw_moves`而非`get_legal_moves`来计算保护范围——因为即使保护者自身被牵制不能移动，它的"保护射线"仍然存在（对方吃被保护子时，保护者可以"解除牵制"吃回）。

### 3.4 炮架与保护的精确区分

这是象棋独有的易混淆概念，LLM极易犯错：

| 概念 | 关系 | 举例 |
|------|------|------|
| **炮架** | 炮隔子吃→被吃方是炮的攻击目标→敌对关系 | 红炮隔黑卒打黑车：黑卒是炮架，黑车被攻击 |
| **保护** | 己方子覆盖己方子→被保护方安全→友方关系 | 红车覆盖红马：红马被红车保护 |

**易错场景**：红炮和红马在同列，中间隔一个子——LLM可能误判为"红炮保护红马"，实际上炮不能"隔子保护"，只能"隔子攻击"。保护必须是直接覆盖（车/马/象/兵可直接保护）。

## 四、难点三：真Agent模式与工具协议设计

### 4.1 问题本质

传统"AI象棋分析"是**硬编码管线**——系统预先定义好分析步骤，LLM只是被动翻译：

```
硬编码管线: FEN → 提取全部标签 → 全部喂给LLM → LLM翻译成自然语言
缺陷: 
  - 用户问"为什么不能走马" → 系统也提取全部45个标签 → 浪费+不聚焦
  - 用户问"整体局势如何" → 系统还是一样的标签 → 无法做战略分析
  - LLM拿到一堆标签后，不知道哪些重要，容易迷失
```

### 4.2 解决方案：Agent化——让LLM自主决定分析路径

**Agent循环**（最多3轮）：

```
Round 1: LLM审视Evidence Map
    → "我发现有is_pinned标签，黑车被牵制，我需要确认牵制来源"
    → 调用 get_threats_to_piece(fen, "黑车-(4,5)")
    → 返回: {"threats": [{"piece": "红车-(4,0)", "line": "column_5"}]}

Round 2: LLM获得牵制信息后深入分析
    → "牵制来自红车，如果吃掉遮挡子，可以直打黑将。让我看看有没有利用机会"
    → 调用 get_move_candidates(fen) → 获取候选走法
    → 调用 analyze_move(fen, candidate_3) → 分析红车走法后果

Round 3: LLM综合信息输出最终分析
    → 不再调用工具 → 输出教练级讲解:
    "当前局面红方占优的关键在于第5路的牵制效果。红车-(4,0)牵制黑车-(4,5)，
     使其无法横走保护黑马-(7,8)。建议红方先走车四进一加强控制，
     黑方如果不解牵制，红方可以直取黑马..."
```

### 4.3 candidate_id协议：杜绝走法幻觉

**问题**：LLM倾向于自行编造走法（如"h2e2"），这些走法可能违反规则（蹩马腿、自将等）。

**解决方案**：

```
Step 1: LLM必须先调用 get_move_candidates(fen)
        → 返回: [
            {candidate_id: "c1", move: "h2e2", piece: "红炮", chinese: "炮二平五"},
            {candidate_id: "c2", move: "h0g2", piece: "红马", chinese: "马八进七"},
            ...
          ]

Step 2: LLM使用 candidate_id 调用后续工具
        → analyze_move(fen, "c1")  ✅ 合法
        → analyze_move(fen, "h9e9")  ❌ 被拒绝（非candidate_id格式）

Step 3: LLM在输出中用 candidate_id 对应的 chinese 描述走法
        → "建议走炮二平五（c1）"  ✅
        → "建议走马三进四"       ❌ 可能违规（未经验证）
```

**原理**：`get_move_candidates`内部调用规则引擎的`get_legal_moves`生成走法——经过了蹩马腿/象眼/自将/照面的完整验证。candidate_id只是这个合法走法的引用标识，确保后续分析的走法一定是合法的。

### 4.4 14个工具的分层设计

**设计决策**：为什么是14个而不是3个"大工具"或30个"微工具"？

```
太粗（3个大工具）：
  "analyze_everything(fen)" → LLM不知道内部做了什么，无法自主组合

太细（30个微工具）：
  "get_rook_attacks(fen)" / "get_cannon_attacks(fen)" → 组合爆炸，LLM选择困难

恰当粒度（14个原子工具）：
  每个工具做一件明确的事，LLM可以像教练一样自主组合：
  "先看全局(get_piece_relations) → 聚焦威胁(get_threats_to_piece) → 深入验证(engine_deep_analysis)"
```

**工具分类设计原则**：

| 类别 | 工具数 | 设计思路 |
|------|--------|----------|
| 棋子关系（查询类） | 4个 | 只读操作，回答"是什么"的问题 |
| 走法分析（推演类） | 5个 | 涉及走法模拟，回答"走了会怎样"的问题 |
| 引擎评估（权威类） | 2个 | 调用Pikafish，是不可争议的数值权威 |
| 知识检索（辅助类） | 3个 | RAG/原则库，提供理论支持 |

## 五、难点四：多专家并行协调与证据裁决

### 5.1 问题本质

三个专家独立分析同一局面，各自输出文本。如何**合并**它们的结论？

**简单拼接的缺陷**：

```
战术专家: "红方应该直取黑马，黑马无根。"
战略专家: "红方子力占优但急于进攻不明智，应该稳固阵型。"
引擎专家: "引擎推荐炮二平五，不是吃马。"

如果简单拼接 → 用户看到三段互相矛盾的文本 → 更困惑
```

### 5.2 解决方案：Claim结构化断言+证据裁决

**Step 1: 每个专家输出结构化Claim**

```python
@dataclass
class Claim:
    statement: str              # "红车控制第五路开放线"
    source: str                 # tool_verified / reasoning / unverified
    confidence: str             # high / medium / low
    evidence: List[EvidenceItem]  # 支持证据链
```

**Step 2: 解析专家输出，提取Claim**

两层解析策略：
1. **显式标记**：解析`[CLAIM]...[EVIDENCE]...[CONFIDENCE]`
2. **隐式回退**：从`【战术发现】`/`【战略评估】`等节标题自动提取

```python
# 显式格式:
[CLAIM] 红车控制第五路开放线，压制黑方右翼
[EVIDENCE] get_piece_attacks(fen, "红车-(0,4)") 返回攻击范围包含(1-9,4)
```

```python
def _infer_source(evidence_text, evidence_chain) -> str:
    # 有工具调用记录 → tool_verified (权重1.0)
    if evidence_chain and evidence_chain.tool_calls:
        return "tool_verified"
    # 包含工具名关键词 → tool_verified
    tool_keywords = ["get_piece_attacks", "engine_deep_analysis", ...]
    if any(kw in evidence_text for kw in tool_keywords):
        return "tool_verified"
    # 包含推理词汇 → reasoning (权重0.7)
    if re.search(r"推理|分析|判断", evidence_text):
        return "reasoning"
    # 默认 → unverified (权重0.3)
    return "unverified"
```

## 七、难点六：SSE流式多线程管线

### 7.1 问题本质

深度分析涉及多个耗时操作（规则提取、引擎评估、多个LLM调用），如何让用户在等待过程中就能看到中间结果？

### 7.2 解决方案：queue + threading + StreamingResponse

**架构**：

```
FastAPI 异步协程
    ↓ 创建 queue.Queue() 共享事件队列
    ↓
    ├─ Thread 1: 预计算（标签+引擎+张力）
    │   → 完成后把结果放入共享数据结构
    │   → event_queue.put({"type": "precompute_done"})
    │
    ├─ Thread 2: 多专家编排
    │   → 战术专家每思考一步 → event_queue.put({"type": "expert_step"})
    │   → 工具调用 → event_queue.put({"type": "expert_tool"})
    │   → 专家完成 → event_queue.put({"type": "expert_result"})
    │   → 合成完成 → event_queue.put({"type": "result"})
    │
    └─ Main: StreamingResponse 异步生成器
        → while True:
            event = event_queue.get(timeout=0.5)
            if event → yield f"data: {json.dumps(event)}\n\n"
            if timeout → yield heartbeat（保持连接）
            if DONE → break
```

**为什么用threading而不是asyncio**：LLM SDK（OpenAI兼容API）的流式调用是同步阻塞的，放在async协程中会阻塞事件循环。threading可以在后台线程中同步等待LLM响应，同时主协程继续消费event queue并推送SSE。

**心跳机制**：0.5秒无事件时发送heartbeat，防止代理/浏览器判定连接超时断开。

## 八、难点七：WebGL物理光学渲染管线

### 8.1 问题本质

Liquid Glass效果需要真实的折射、色散、菲涅尔等物理光学效果。CSS的`backdrop-filter: blur()`只能做简单模糊，无法实现光线穿过玻璃材质时的物理行为。

### 8.2 解决方案：4遍WebGL自定义渲染管线

**渲染管线详解**：

```
Pass 1: 背景采样 (fragment-bg.glsl)
    输入: 背景canvas纹理
    输出: FBO[0] — 带SDF圆角矩形裁切的背景
    技术: Superellipse SDF (u_shapeRoundness控制方圆度)
          + 阴影扩展 (u_shadowExpand/u_shadowFactor)
    
Pass 2: 垂直高斯模糊 (fragment-vblur.glsl)
    输入: FBO[0]
    输出: FBO[1] — 垂直方向模糊
    技术: 可变半径高斯核 (u_blurRadius=0-200)
          权重数组 u_blurWeights[MAX_BLUR_RADIUS]（最多201个采样点）
    
Pass 3: 水平高斯模糊 (fragment-hblur.glsl)
    输入: FBO[1]
    输出: FBO[2] — 完成双向模糊 = 折射用模糊背景
    技术: 同Pass 2，正交方向
    
Pass 4: 折射合成 (fragment-main.glsl)
    输入: FBO[2](模糊背景) + 原始内容纹理
    输出: 最终屏幕画面
    物理效果:
      ① 折射: UV偏移采样模糊背景
         refOffset = coord / resolution * u_refFactor
      ② 色散: RGB三通道不同偏移量
         R = sample(uv + offset * (1 - dispersion))
         G = sample(uv + offset)
         B = sample(uv + offset * (1 + dispersion))
      ③ 菲涅尔: 边缘更强的反射
         fresnel = pow(1.0 + merged_sdf, 5.0)
      ④ 炫光: 定向高光
         glare = func(angle, convergence, hardness)
```

### 8.3 物理光学效果原理

**折射（Refraction）**：
光穿过玻璃时，方向发生偏折。在2D中表现为：采样模糊背景时，UV坐标发生偏移。偏移量由`u_refFactor`（折射率）和片段位置决定。

**色散（Chromatic Dispersion）**：
不同波长的光折射率不同——红光折射少，蓝光折射多。实现方式：对R/G/B三个通道分别采样，偏移量不同：R通道偏移×(1-dispersion)，B通道偏移×(1+dispersion)，产生彩虹边缘效果。

**菲涅尔效应（Fresnel）**：
玻璃边缘处反射更强——正视玻璃中央几乎透明，斜视边缘处反射明显。用`pow(edge_factor, 5.0)`模拟（5次幂产生急剧的边缘增强效果）。

**炫光（Glare）**：
模拟光源在玻璃表面的高光反射，可配置方向角(`u_glareAngle`)、扩散(`u_glareRange`)、强度(`u_glareFactor`)、焦点收敛度(`u_glareConvergence`)。

### 8.4 为什么不用Three.js

| 对比 | Three.js | WebGL原生（本项目） |
|------|----------|-------------------|
| FBO管理 | 框架抽象，难以精确控制pingpong | 手动管理4个FBO，完全可控 |
| 自定义Pass | 需要用ShaderPass适配 | 直接定义Fragment Shader |
| 性能 | 框架开销（场景图/相机/材质） | 零开销，仅全屏四边形 |
| 打包体积 | Three.js约500KB | 仅5个GLSL + 渲染器<200行 |
| DPR处理 | 框架抽象 | 手动`devicePixelRatio`适配 |
