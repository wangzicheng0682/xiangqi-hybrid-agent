# 作品简介

## 一、项目概述

### 1.1 项目名称
**象棋AI混合代理教学与对弈系统**（Xiangqi Hybrid Agent Teaching & Game System）

### 1.2 一句话定义
让AI像教练一样**读懂棋局**、**讲解棋局**，而不是念坐标。

### 1.3 项目定位
基于神经符号AI架构的象棋教练系统，通过Evidence Map约束大模型输出，实现零幻觉的棋局分析。

---

## 二、项目背景与意义

### 2.1 象棋教学现状痛点

| 痛点 | 描述 | 现有解决方案 |
|------|------|-------------|
| **学习门槛高** | 象棋入门需要理解开局原则、中局战术、残局技术，自学难度大 | 视频教程、棋谱书籍 |
| **反馈不及时** | 学习者走棋后无法立即获得专业点评 | 搜索引擎、请教老师 |
| **分析工具专业性不足** | 现有引擎只给评分，不解释原因 | Stockfish、象棋巫师 |
| **LLM幻觉严重** | 通用AI分析象棋时经常编造棋子位置、伪造战术关系 | 无有效解决方案 |

### 2.2 现有方案缺陷

**传统象棋引擎（如Stockfish）的局限：**
- 只输出评分和推荐走法，不解释"为什么"
- 输出结果难以被非专业棋手理解
- 无法提供个性化的学习指导

**通用大语言模型的局限：**
- 象棋规则理解不精确（马腿、象眼、九宫等）
- 棋子位置描述容易"编造"（幻觉问题）
- 缺乏专业的象棋术语和棋理知识
- 无法与专业象棋引擎协同

### 2.3 项目意义

本项目旨在解决上述痛点，通过**规则引擎+LLM混合架构**，实现：
- ✅ 专业级棋局分析（教练式讲解）
- ✅ 零幻觉的事实保证（Evidence Map约束）
- ✅ 实时思考过程展示（多专家并行+SSE流式输出）
- ✅ 可解释的AI决策（工具调用+证据链）

## 三、核心功能

### 3.1 深度分析模式

**功能描述：** 用户点击"深度分析"后，系统启动三专家并行分析，通过SSE流式返回实时思考过程。

**技术流程：**
```
用户点击深度分析
    ↓
协调器(OOrchestrator)接收请求
    ↓
张力检测器分析局面复杂度
    ↓
┌─────────────────────────────────────┐
│     三专家并行分析                    │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐│
│  │ 战术专家 │ │ 战略专家 │ │ 引擎专家 ││
│  │ Tactics │ │Strategy │ │ Engine ││
│  └────┬────┘ └────┬────┘ └────┬────┘│
│       └───────────┼───────────┘      │
│                   ↓                  │
│            合成器(Synthesizer)        │
│         综合三方结论→统一讲解          │
└─────────────────────────────────────┘
    ↓
SSE流式输出：专家思考过程→综合讲解
```

**输出内容：**
- 三位专家的分析结论（战术/战略/引擎视角）
- 协调者的综合讲解（教练式语言）
- 实时思考步骤展示（像特级大师一样思考）
- 证据链支撑（每条结论有事实依据）

### 3.2 快速分析模式

**功能描述：** 响应时间<1秒，返回棋局基本信息。

**输出内容：**
- 45个战术标签检测结果
- 引擎评估分数和最佳走法
- 张力类型分析（局面中的矛盾点）
- 走法质量评估（失误、吃子、将军等）

### 3.3 棋谱管理

**功能描述：** 支持PGN棋谱导入、历史对局检索、局面相似度匹配。

**技术实现：**
- Neo4j图数据库存储19万局历史对局
- 支持按红方、黑方、结果、日期搜索
- 相似局面检索（给定FEN找类似对局）

### 3.4 引擎评估

**功能描述：** 集成Pikafish（中国象棋版Stockfish）进行深度计算。

**技术实现：**
- UCI协议封装
- 连接池管理（消除200ms启动开销）
- MultiPV多候选分析
- 胜率折线图可视化

### 3.5 走法模拟

**功能描述：** 用户走棋前可预览走法效果。

**输出内容：**
- 走法前后的标签差异对比
- 将军/将死/困毙检测
- 吃子信息（吃什么、被吃什么）
- 战术组合预览

### 3.6 RAG知识检索（创新功能）

**功能描述：** 基于ChromaDB向量数据库的语义检索系统，为AI分析提供棋理知识支撑。

**技术实现：**
- **ChromaDB向量存储**：使用text2vec-base-chinese做中文嵌入
- **80+棋理原则自动索引**：首次访问时懒加载
- **14万局棋谱开局索引**：按需构建（前5000局自动索引）
- **三种检索模式**：
  - 语义检索：`retrieve(query, top_k)` - 自然语言查询
  - 按阶段过滤：`retrieve_by_phase(query, phase)` - 开局/中局/残局
  - 按类型过滤：`retrieve_by_type(query, doc_type)` - 原则/棋谱

**Agent工具集成：**
```python
search_chess_knowledge(query="中炮开局攻势", top_k=5)
# 返回：相关棋理原则 + 经典开局参考
```

### 3.7 对弈模式（创新功能）

**功能描述：** 人机对弈，支持三级难度，满足不同水平用户需求。

**API端点：** `POST /api/game/ai-move`

**三级难度：**
| 难度 | 引擎深度 | 适用场景 |
|------|----------|----------|
| easy | depth=4 | 初学者入门 |
| medium | depth=10 | 进阶玩家 |
| hard | depth=18 | 高手挑战 |

**返回信息：**
- `move`：UCI格式走法（如"h2e2"）
- `move_chinese`：中文走法描述（如"红炮二平五"）
- `score`：引擎评估分数
- `depth`：实际搜索深度
- `fen_after`：走完后的FEN
- `in_check`：走完后对方是否被将军
- `game_over`：是否将杀/和棋

**安全保障：**
- 合法性双重验证（引擎走法 + RuleEngine校验）
- 将杀局面自动识别

## 五、技术指标

### 5.1 标签检测体系

| 指标 | 数值 | 说明 |
|------|------|------|
| 标签总数 | 45个 | 覆盖象棋所有战术类型 |
| 检测方法 | 100%规则硬判定 | 置信度二元化（0或1） |
| 准确率 | 100% | 无模型幻觉 |
| 检测层级 | 9大层级 | 将杀/捉子/闪击/牵制/杀法/子力/走法/战略/引擎 |

**九大检测层级：**
1. 将杀困毙层（3个）：is_check, is_checkmate, is_stalemate
2. 捉子层（3个）：is_attack_unprotected, is_mutual_attack, is_attack_king_adjacent
3. 闪击抽将层（3个）：is_discovered_check, is_double_attack, is_discovered_attack
4. 牵制串打层（2个）：is_pinned, is_cannon_double_attack
5. 标准杀法层（8个）：马后炮、铁门栓、双车错、卧槽马、白脸将、重炮杀、海底捞月、侧面虎
6. 子力状态层（2个）：piece_is_unprotected, cannon_has_platform
7. 走法质量层（6个）：move_is_blunder, move_is_capture, move_gives_check等
8. 战略评估层（5个）：controls_open_file, has_active_pieces, piece_coordination等
9. 引擎对齐层（3个）：engine_only_move, engine_best_by_margin, engine_forcing_sequence

### 5.2 张力检测

| 指标 | 数值 | 说明 |
|------|------|------|
| 张力类型 | 6种 | 自动识别局面矛盾 |
| 触发条件 | 可配置 | 默认cp>300 |

**张力类型：**
- 评估异常（引擎评估与标签检测矛盾）
- 子力vs攻势（物质优势与攻势速度的冲突）
- 危机中的资源（危险但有潜在反击手段）
- 沉睡的棋子（强子未发挥作用）
- 标签矛盾（不同标签描述互相矛盾）
- 阶段错位（局面特征与预期阶段不符）

### 5.3 Agent系统

| 指标 | 数值 | 说明 |
|------|------|------|
| 专家数量 | 3个 | 战术/战略/引擎 |
| 并行模式 | 自适应 | 根据张力数量选择 |
| 工具数量 | 12个 | 原子化设计 |
| 工具调用 | Function Calling | LLM主动决策 |
| 最大轮次 | 3轮 | 防止无限循环 |

### 5.4 性能指标

| 指标 | 数值 | 说明 |

## 六、创新点

### 6.1 零幻觉架构（核心创新）

**问题：** 通用LLM在棋类分析中最大的问题是"编造"——编造棋子位置、伪造战术关系。

**解决方案：** Evidence Map约束机制
- 规则引擎负责"事实提取"（100%准确）
- Evidence Map作为"事实锚点"传递给LLM
- LLM只负责"教练式表达"，不能编造事实

**技术实现：**
- 45个战术标签基于规则硬判定
- 每条标签绑定具体棋子坐标
- LLM的System Prompt明确禁止编造
- 工具调用结果作为证据验证

### 6.2 真Agent模式

**问题：** 大多数"AI象棋"是硬编码流程，LLM只是被动回答。

**解决方案：** LLM主动调用工具分析
- 12个专业工具供LLM自主选择
- 最多3轮调用循环
- 像教练一样思考的Agent

**工具列表：**
| 类别 | 工具 | 用途 |
|------|------|------|
| 棋子关系 | get_piece_attacks | 获取棋子攻击范围 |
| | get_piece_defenders | 查询棋子保护关系 |
| | get_threats_to_piece | 查询棋子受威胁情况 |
| | get_piece_relations | 综合关系查询 |
| 走法分析 | get_move_candidates | 获取合法候选走法 |
| | analyze_move | 深度分析走法效果 |
| | compare_moves | 对比多步棋优劣 |
| | get_forcing_sequence | 分析强制序列 |
| | simulate_move | 模拟走棋并对比标签差异 |
| 引擎分析 | engine_deep_analysis | 引擎深度分析 |
| | engine_alternatives | 候选走法对比 |
| 知识检索 | query_chess_principles | 检索局面适用棋理原则 |
| | search_chess_knowledge | 语义检索象棋知识库（ChromaDB RAG） |

### 6.3 特级大师思维链

**问题：** 通用LLM不懂"开局要快出大子"这类阶段特定原则。

**解决方案：** 阶段感知的思维框架
- 开局十大原则
- 中局战略分析
- 残局精确计算
- Few-shot示例库

**阶段检测规则：**
| 阶段 | 条件 | 思维重点 |
|------|------|----------|
| 开局 | move_count <= 15 且 total_pieces >= 26 | 出子效率、中心控制、先手争夺 |
| 中局 | 15 < move_count < 60 | 子力纠缠、战术组合、局面转换 |
| 残局 | total_pieces <= 14 或 move_count >= 60 | 王的安全、兵的位置、取胜技术 |

### 6.4 三专家并行架构

**创新点：** 战术、战略、引擎三个Agent并行分析，合成器综合结论。

**架构优势：**
- 并行处理提高响应速度
- 多角度分析提高准确性
- 结构化断言便于证据裁决
- 自适应决策（简单局面单Agent，复杂局面多Agent）

### 6.5 证据裁决机制

**创新点：** 合成器不是简单的文本合并，而是"证据裁判"。

**机制实现：**
- 每条专家结论标记来源（tool_verified / reasoning / unverified）
- 合成器交叉验证证据链
- 证据权重裁决（工具验证>推理>未验证）
- 输出包含【证据基础】段落

## 七、应用场景

- **场景：** 初学者想理解每步棋的原因

- **场景：** 赛后复盘、失误分析
- **价值：** 实时流式展示AI思考过程

### 7.4 内容创作者
- **场景：** 生成棋局解说文字
- **价值：** 自动生成教练级讲解
- **效果：** 大幅提升内容创作效率

### 7.5 人机对弈练习
- **场景：** 用户选择难度与AI对弈

## 八、用户体验

### 8.1 界面设计理念

> "设计，为专注而生"

**核心原则：**
- 摒弃冗余的炫酷，回归体验的本质
- 以空间感，构建界面的秩序
- 用材质的差异，划分清晰的层级
- 降低认知负担，让注意力回归棋局本身
- 让技术隐于无形，让用户聚焦核心

### 8.2 Liquid Glass设计系统

采用Apple iOS 26液态玻璃设计语言：

**8层背景层次：**
- 颗粒噪点层（电影级颗粒感）
- 顶部深墨晕染（水墨书卷气）
- 左上自然光晕（模拟自然光感）
- 玻璃模糊层（blur: 28px saturate: 200%）
- 内层湿润高光（玻璃厚度感）
- 边缘折射光（物理光学效果）
- 阴影层（立体感）

**WebGL四步渲染管线：**
```
bgPass → vBlurPass → hBlurPass → mainPass → 屏幕
```

**物理光学参数：**
```css
--glass-blur: blur(28px) saturate(200%);
```
