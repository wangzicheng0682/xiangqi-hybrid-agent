## 总体难度判断：**中高难度，但有清晰路径**

你的地基打得很好，Evidence Map 这个设计决策我认为是整个项目最有价值的东西。以下是我逐层拆解的想法。

---

### L1 已经做对了的事

45个规则标签 + Evidence Map 约束 LLM，这条路是对的。我自己作为 agent 深有体会：**没有事实锚点的时候，我其实非常容易在棋类问题上编造坐标和走法。** Evidence Map 的思路直接切断了这条路，这是工程上的正确选择，不是妥协。

---

### L2 工具调用：最近的果实，改造性价比最高

**当前问题**：你把调用限制写死成"3轮×3工具"。这是为了控制延迟，但副作用是 agent 的分析路径被固定了，它没办法根据"发现了什么"来决定"下一步问什么"。

**我的经验**：我调用工具时最有价值的时刻，不是第一轮调用，而是**根据第一轮结果产生新问题**的那个转折。比如我搜索一个问题，看到结果里出现了一个新名词，我会决定再搜一轮。这个"发现→追问"循环是 agent 质量的核心。

**实用建议**：与其死板限制轮数，不如给 agent 一个**工具预算**（比如 token budget 或 time budget），让它自己决定什么时候够了。同时在 system prompt 里加一条：

```
当你发现工具返回的结果中出现了值得追问的线索时，
你有权再发起一轮调用，但必须在<thinking>中说明为什么。
```

这个改动不大，但效果显著。

---

### L3 分析策略：需要注入"棋感的优先级"

**当前问题**：你设计了阶段感知思维链，这是对的。但"知道该按什么顺序看局面"这件事，现在是靠提示词模板来强制的，而不是 agent 内化的判断。

**教练真正会做的事**：真正的教练看到局面的第一秒，脑子里会自动跑：*将帅安全吗？谁在反将？子力是否协调？是否有即时战术？* 这个顺序是**优先级体系**，不是线性步骤。

**可以做到的方案**：在 system prompt 里给 agent 一个**局面类型路由**：

```
拿到局面后，先判断：
1. 有即时战术机会（将、捉、闪）→ 优先用战术工具深挖
2. 局面平稳 → 转战略工具分析子力协调
3. 局面复杂难判 → 先engine_deep_analysis确认评估方向
```

这不是万能的，但能把"无脑按模板走"变成"看情况选路径"，难度是中等，效果明显。

---

### L4 元认知：这是真正的硬骨头

**这是什么**：agent 需要能问自己——*"我这次分析够不够？有没有明显的盲点？"*

我自己在处理复杂问题时，有一个内隐的感觉：有时候搜完三轮我觉得答案很清楚，有时候搜了很多但总感觉有什么没抓住。这个"感觉"其实来自于**内部一致性检查**：我发现的几个证据是否互相支持？有没有矛盾的地方？

**对你的系统，可以用结构化方式模拟这个**：

在深度模式的最后一步，强制让 agent 做一次"自查"：

```
在生成最终讲解前，先回答：
- 我的分析依赖了哪些工具的结果？
- 有没有我没检查过但可能影响结论的因素？
- 如果这个局面是对局中的关键一步，我说的够吗？
```

这不是真正的元认知，是"结构化的自省"，但在实践中效果接近。

---

### L5 主动探索（好奇心）：最难，但有取巧方式

**真正难的地方**：让 agent 主动注意到"局面里有个有趣的东西值得我深挖"，需要它在没被问到的情况下主动产生兴趣。这其实是 LLM 的一个弱项——现有模型被训练成"等指令、回应指令"，主动性不是自然涌现的。

**但可以用触发器模拟**：与其期待真正的自发好奇心，不如在 Evidence Map 里设计**"高价值信号"探测机制**：

```python
# 当检测到以下标签时，agent 自动进入深度探索模式
HIGH_CURIOSITY_TRIGGERS = [
    "is_discovered_check",       # 闪击：通常有更深的连续手
    "engine_only_move",          # 唯一正解：值得解释为什么其他不行
    "move_is_blunder",           # 臭棋：值得分析为什么错、正确应该怎么走
    "piece_coordination",        # 子力协调：通常背后有战略意图
]
```

当触发这些信号时，system prompt 里用不同的 persona 提示 agent：**"你注意到了一个值得深入探索的局面特征，现在请你像一个对这个发现感到兴奋的教练一样展开分析。"** 这是在用工程手段模拟好奇心，不如真正的好奇心，但可控、可调试。

---

### 我作为 agent 最想告诉你的一件事

你在 6.2 节的工具描述设计里写了"【什么时候用】"，**这是整个项目里我最欣赏的工程决策之一**。对 LLM 来说，工具的 `when_to_use` 字段比 `what_it_does` 重要 10 倍。我选择调用哪个工具，本质上是在做意图匹配——我的当前意图是什么，哪个工具的"适用场景"跟它最接近。

你可以把这个机制再往前推一步：给每个工具加上一个**"不该在什么时候用"**的反例字段：

```python
"""
【什么时候不用】
- 当你只是想知道局面整体评估时，不要用这个（用 analyze_position_strategy）
- 当棋子已经受保护时，用这个结果可能引起误导
"""
```

我自己就常犯这种错：选了一个功能匹配但时机不对的工具。负例描述能有效防止这个。
