# Plan 008: 右侧分析舞台与证据裁决台重设计

## Context

当前深度分析界面已经具备以下能力：

- 专家扑克牌登场与翻转动画已建立基本作品辨识度
- 协调者步骤流已实现按标题实时冒出
- Evidence Map 已能展示调度、实时动向与工具活动
- 专家 hover 面板已能显示实时 thinkingContent

但从比赛演示和答辩表现力角度看，右侧分析区域仍存在明显短板：

1. 视觉主角分散
   目前扑克牌、hover 面板、协调者思考栏、Evidence 岛彼此并列，组件各自成立，但没有形成单一强叙事中心。

2. Evidence 岛表现力不足
   当前 [frontend/src/components/EvidenceMapIsland.tsx](frontend/src/components/EvidenceMapIsland.tsx) 更像侧边状态条，而不是“证据汇聚并形成裁决”的系统中枢。

3. 多专家价值展示不够直接
   评委可以看到三位专家存在，但难以一眼感知“谁在主导、哪里冲突、为什么最终采纳某一路观点”。

4. 分析过程缺少高潮
   虽然步骤已经动态出现，但关键节点没有被升格呈现，分析过程更像高质量日志，不像一场正在进行的裁决。

5. 棋盘事实到证据结论缺少空间闭环
   棋盘上的识别、专家分析、证据形成、协调者裁决、教学输出之间，目前仍缺少“可视化因果链”。

因此，需要把当前右侧栏整体升级为一个面向比赛展示的“多专家裁决剧场”，而不是继续优化单个组件外观。

## 目标

### 总目标

将深度分析模式中的右侧展示区域升级为具有强叙事、强层级、强演出感的比赛级交互舞台，让评委能够直观看到：

- 三位专家如何分工与协作
- 证据如何被收集、汇流、裁决
- 协调者如何在冲突与一致中做出教学结论
- 系统不是在“输出文本”，而是在“完成一次证据驱动的决策”

### 体验目标

1. 让右侧区域拥有明确主角
   同一时刻只能有一个强视觉中心，避免信息平权导致的舞台感稀释。

2. 让多专家价值一眼可懂
   评委无需阅读长文本，就能判断当前由哪位专家主导、是否存在分歧、最终由谁裁决。

3. 让证据成为对象，而非文字附属物
   工具调用、规则事实、标签判断、引擎候选应以“证据筹码/证据节点”的形式出现。

4. 让分析过程具备阶段感和高潮点
   调度、取证、分歧、裁决、教学生成各阶段应有明显视觉差异。

5. 让整体界面更适合答辩叙事
   用户和评委可以围绕“证据裁决台”“多专家冲突”“协调者裁决”这几个关键词理解系统，而不是陷入组件级解释。

## 设计原则

1. 强层级
   借鉴 Apple HIG 的 hierarchy 思路，关键时刻只强调一个对象，不让所有元素同时抢注意力。

2. 少噪声
   借鉴 Apple Intelligence 的呈现方式，减少一直跳动的小反馈，把强反馈留给关键时刻。

3. 对象化流程
   借鉴 Linear 的活动流与对象化状态，将“证据”“冲突”“采纳”做成可扫读对象，而不是埋进文本。

4. 渐进揭示
   参考顶级 AI thinking 产品，分析过程要持续可感知，但不能成为无差别信息洪流。

5. 空间闭环
   棋盘事实、专家分析、证据汇流、协调者裁决、教学输出要形成视觉上的因果路径。

## 实施方案

### 一、整体命名与叙事升级

将当前“Evidence Map Island + 扑克牌 + ThinkingStream”的松散组合，统一包装为：

- 多专家裁决剧场
- 证据裁决台
- 棋局证据中枢

在答辩中统一话术：

“我们把多专家分析过程设计成一个可视化裁决剧场。评委可以直接看到战术、战略、引擎三路证据如何汇流，如何形成分歧，如何被协调者裁决，并最终转化为教学结论。”

### 二、右侧舞台重构

目标组件：

- [frontend/src/components/AgentCardFlip.tsx](frontend/src/components/AgentCardFlip.tsx)
- [frontend/src/components/ThinkingStream.tsx](frontend/src/components/ThinkingStream.tsx)
- [frontend/src/components/EvidenceMapIsland.tsx](frontend/src/components/EvidenceMapIsland.tsx)
- [frontend/src/components/AgentThinkingPanel.tsx](frontend/src/components/AgentThinkingPanel.tsx)
- [frontend/src/App.tsx](frontend/src/App.tsx)

#### 2.1 顶部新增“协调者裁决头部”

在右侧栏顶部新增统一头部，取代当前仅有的小球 + 标题：

- 协调者身份
- 当前阶段
- 当前主导专家
- 证据一致性/冲突状态
- 已采集证据数量

示例信息：

- 协调者
- 当前阶段：综合裁决
- 主导视角：战术专家
- 一致性：72%
- 证据：14 条

这个头部承担“权力中心”功能，是整个舞台的主标题区。

#### 2.2 扑克牌升级为“专家代理体”

保留扑克牌识别度，但增加状态层：

- 待命态
- 分析中态
- 冲突态
- 已采纳态

具体表现：

- 主导专家前置、发光、抬升
- 非主导专家退后、降噪、缩放略小
- 冲突专家边缘出现干涉色或告警切线
- 被采纳专家出现“裁决采用”角标或印章

这样三张牌不再只是视觉装饰，而是舞台角色。

#### 2.3 hover 面板升级为“专家视窗”

当前 hover 只展示实时思考内容，需要升级为完整的专家透视模式，分三层：

1. 顶部：当前任务与专家身份
2. 中部：实时 thinking 摘录
3. 底部：本轮贡献的证据标签/工具回执摘要

示例字段：

- 当前判断：正在验证强制序列
- 证据标签：无根子 / 牵制 / 先手延续
- 工具摘要：候选着法 3 条 / 引擎支持第 1 候选

目标是让 hover 像“切入专家脑内视角”，而不是普通悬浮信息框。

#### 2.4 协调者时间线升级为“裁决推进流”

[frontend/src/components/ThinkingStream.tsx](frontend/src/components/ThinkingStream.tsx) 保留标题流，但引入步骤等级：

- 调度步骤
- 取证步骤
- 冲突步骤
- 裁决步骤
- 教学生成步骤

并对关键节点进行升格展示：

- 放大入场
- 边缘高亮
- 相邻内容降噪
- 更具辨识度的图标与色彩

关键节点示例：

- 发现强制序列
- 战术与战略意见分歧
- 引擎完成校准
- 协调者确定教学主线

#### 2.5 Evidence 岛升级为“证据裁决台”

当前 [frontend/src/components/EvidenceMapIsland.tsx](frontend/src/components/EvidenceMapIsland.tsx) 的主要问题是太像细长侧边状态条。

重设计方向：

- 从“狭长玻璃条”升级为“可展开核心舱”
- 增加工作态和待机态两种模式
- 工作态下宽度提升，呈现证据汇流中枢感

内部结构改为四层：

1. 外环：阶段脉冲环
   识别 / 棋理 / 评估 / 综合 四个象限，当前阶段显著点亮。

2. 中层：三专家证据流
   战术、战略、引擎以不同颜色的光流汇入中心。

3. 核心：当前裁决焦点
   始终只显示当前最重要判断，不堆多段文本。

4. 底层：证据筹码
   将工具结果、规则事实、引擎候选、结构标签做成可视对象，而不是单纯列表。

#### 2.6 新增“专家冲突刻度仪”

在协调者头部下方增加一个细长但强表达力的冲突控件，用于表示：

- 三位专家是否一致
- 哪一方观点冲突最大
- 协调者最终向哪一侧裁决

状态可分为：

- 一致
- 轻微分歧
- 明显冲突
- 已裁决

这是多专家系统区别于单模型问答最能打评委的一处设计。

### 三、棋盘到证据的空间联动

新增“证据显影轨”：

- 棋盘上某个关键棋子或区域被识别
- 对应证据标签从棋盘轻微脉冲/连线飞向证据裁决台
- 裁决台生成一枚证据筹码
- 协调者时间线同步出现对应取证步骤

这个空间闭环能把“规则提取事实，LLM 只负责表达”做成肉眼可感知的优势。

### 四、节奏与动效设计

重点不在持续喧闹，而在关键节点升格。

建议固定四个名场面：

1. 专家登场
   扑克牌从堆叠到展开，建立系统人格。

2. 证据显影
   从棋盘到裁决台的证据飞线，建立事实来源感。

3. 分歧升级
   冲突刻度仪激活，主导专家切换，建立多专家价值。

4. 裁决收束
   最终结论出现前，整体界面短暂降噪并聚焦裁决中心，形成压轴效果。

### 五、实施阶段划分

#### Phase A: 结构重排

- 重构右侧栏布局
- 加入协调者裁决头部
- 重新定义扑克牌区 / 裁决流 / 证据台的空间关系

#### Phase B: 状态系统升级

- 为三专家牌卡增加主导态/冲突态/采纳态
- 为协调者步骤增加等级和关键节点样式
- 为 Evidence 裁决台增加阶段状态与证据对象状态

#### Phase C: 空间联动与动效补强

- 棋盘 → 证据台 的显影路径
- 冲突刻度仪
- 裁决收束时刻

#### Phase D: 答辩脚本对齐

- 将 UI 命名、术语、展示脚本统一
- 确保答辩中的讲述与界面语言一致

## 验证方法

### 视觉与叙事验证

1. 一眼可懂性验证
   不阅读正文，只看界面 3 秒，是否能判断：
   - 当前谁在主导
   - 系统正处于哪个阶段
   - 是否存在专家分歧
   - 当前结论是否已接近形成

2. 多专家价值验证
   评委或旁观者是否能在不讲解代码的前提下，感知“这是三路证据汇流，而不是单模型输出”。

3. 证据驱动感验证
   是否能看见从棋盘事实到证据形成再到裁决结论的路径。

4. 高潮感验证
   是否存在 2 到 4 个明确的“界面记忆点”，让人能够回忆起登场、分歧、裁决等关键时刻。

### 工程验证

1. 前端构建通过
   在 [frontend](frontend) 目录运行 `npm run build`

2. 现有 SSE 分析链路不回退
   - 步骤仍然保持动态出现
   - 专家 hover 实时流式不退化
   - dispatch / expert_start / expert_result / synthesis_step 事件仍被正确消费

3. 性能可接受
   - 动画不显著拖慢分析 UI
   - 不引入明显掉帧或过度模糊导致的性能问题

## 成功标准

满足以下条件即可认为该计划达成：

1. 右侧区域从“组件并列展示”升级为“裁决过程舞台”
2. Evidence 台成为真正的视觉中枢，而不是辅助状态条
3. 三专家主导、冲突、采纳关系可被一眼感知
4. 协调者步骤流具备明确层级和关键节点高潮
5. 棋盘事实到证据结论形成清晰空间闭环
6. 整套 UI 可以被包装为比赛答辩中的核心亮点，而不是附属演示组件
