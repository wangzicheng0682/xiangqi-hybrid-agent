# Plan: 比赛级长期实施路线图

## Context

项目的最终目标不是“做一个能分析象棋的系统”，而是做一个在比赛现场、评委追问、演示波动和复杂局面下，仍然能证明自身可靠、有效、可解释的作品。

当前系统已经有三个很重要的基础：

1. 规则即事实：标签检测和 Evidence Map 是非常正确的方向。
2. 多视角解释：战术、战略、引擎三个视角有教学价值。
3. 可流式展示：前端已经具备较好的讲解和过程可视化能力。

但要达到比赛级，不是继续横向堆功能，而是要做四件更难的事：

1. 让系统失败得更少。
2. 让系统出错时诚实可见。
3. 让系统结论有量化支撑。
4. 让系统的每一层都能讲清楚为什么这样设计。

这份路线图定义的是长期实施路径，不替代单项技术方案，而是作为所有后续计划的总上位图。

## 总目标

在比赛交付前，系统要达到以下 5 个结果：

1. **可靠**：高频分析请求下稳定工作，不频繁失败。
2. **可控**：LLM 不再自由编造关键动作与证据。
3. **可证**：能用指标证明系统比初版更强。
4. **可讲**：评委能理解架构为什么有效，而不是觉得只是“提示词工程”。
5. **可演示**：前端展示、分析流程、异常降级在现场都稳定。

## 核心战略

### 战略 1: 先下限，后上限

先解决失败率、非法走法、伪成功，再追求更强的棋力、更深的知识库、更炫的表达。

### 战略 2: 让 LLM 退出高风险决策位

LLM 应该负责：

1. 解释
2. 排序
3. 归纳
4. 教学表达

LLM 不应该负责：

1. 自由生成走法
2. 重建棋盘空间关系
3. 伪造证据
4. 在证据缺失时继续输出确定性结论

### 战略 3: 所有增强都要能转化为答辩资产

一个改动如果不能帮助提升：

1. 稳定性指标
2. 解释质量
3. 评委可理解性
4. 现场演示稳健性

就不应该排在高优先级。

## 总体阶段划分

路线分为 6 个阶段，每一阶段都有清晰产出、验收门槛和止损点。

## Phase 0: 架构止血

### 目标

先把系统从“经常失败且失败不透明”拉到“可以稳定运行且失败可见”。

### 范围

1. 统一可靠性客户端
2. 门控式专家调度
3. 失败感知合成器
4. 结构化错误码与状态

### 当前状态

已启动，并已完成第一轮主干落地。

### 成功标准

1. 分析状态可区分 success / degraded / partial / failed
2. 429 不再直接打死主流程
3. 少于关键专家阈值时系统显式降级
4. 全量回归测试通过

### 止损点

如果这一阶段做不稳，后续所有功能建设都应延后。

## Phase 1: 动作空间约束

### 目标

彻底解决“模型乱写走法、混用坐标与 UCI”这一类系统性错误。

### 范围

1. 引入 candidate_id / move_id 协议
2. 先由规则层或引擎层生成合法候选
3. 工具只接收候选 ID 或统一校验后的 move
4. 专家 prompt 删除自由写走法暗示

### 产出

1. `core/llm/move_candidate_service.py`
2. 工具协议升级
3. 兼容旧接口的 validator 层
4. 非法走法拦截测试

### 当前状态

✅ **Phase 1 核心完成**：
- 候选走法服务 + candidate_id 工具协议 + 专家/单Agent schema 全部接入
- RuleEngine 改为纯Python合法走法生成（不依赖 perft 子进程）
- 自将过滤 + 将帅照面 + 攻击范围/合法走法分离 全部正确
- 15项规则正确性回归测试
- 前端消费与证据展示仍待继续收口

### 成功标准

1. 主流程不再出现非法走法字符串
2. 所有分析工具可回溯候选来源
3. 专家更像“在候选上决策”，而不是“凭空发明动作”

### 风险

1. 会影响现有 prompt 和工具 schema
2. 需要处理新旧协议共存期

### 为什么这一阶段重要

这是从“能跑”到“可信”的关键一刀。没有这一步，可靠性永远只是补丁式的。

## Phase 2: 证据裁决化

### 目标

让合成器真正成为“裁判”，而不是“文本合并器”。

### 范围

1. 让专家输出结构化 claim / evidence / uncertainty
2. 合成器按证据权重裁决，而不是按文本风格综合
3. 支持冲突解释：为什么战术专家和引擎专家不一致
4. 明确结论置信度的由来

### 产出

1. 结构化 expert_result schema v2
2. claim-evidence 对齐协议
3. synthesis 证据权重规则
4. 冲突样例回归集

### 成功标准

1. 综合结论能说清：依据是什么、缺什么、为什么可信度是这个级别
2. 评委追问“为什么这么判断”时，系统架构上有可解释答案
### 当前状态

✅ **Phase 2 主干落地**：
- `core/llm/claim.py`：Claim/EvidenceItem/EvidenceChain 数据结构 + 双模式解析器
- ExpertResult v2：新增 claims + evidence_chain 字段
- 工具输出回填：tool_calls_log 现在记录 result_summary
- 三专家 prompt：末尾新增 [CLAIM][EVIDENCE][CONFIDENCE] 输出要求
- 合成器：从"综合裁判"升级为"证据裁决者"，断言对齐 + 证据交叉验证
- 20项 Phase 2 回归测试
- 待跟进：真实 LLM 调用下验证 claim 输出率、冲突样例回归集
### 止损点

如果这一阶段难度过高，可先做“失败感知 + 证据列举”弱版本，再迭代到严格裁决。

## Phase 3: 案例知识化

### 目标

把系统从“抽象棋理解释器”升级为“案例驱动的教学系统”。

### 范围

1. 建立高质量典型局面集
2. 为每个局面标注：局面类型、主要张力、最佳计划、常见误判、反例
3. 构建失败案例库，专门吸收系统历史错误
4. 把案例知识接入讲解与评测

### 产出

1. 200-500 个标注局面
2. 系统失败样本库
3. 教学案例解释模板
4. 案例检索或轻量案例映射模块

### 成功标准

1. 系统讲解不再只是“像高手在说话”，而是更像“教练拿案例在教”
2. 历史失败能被纳入持续迭代，而不是一次性修补

### 风险

1. 标注成本高
2. 如果没有明确格式，案例库很容易变成散乱素材堆

### 原则

这一阶段优先做“高质量、少量、强标注”，而不是大而泛的数据堆积。

## Phase 4: 比赛评测体系

### 目标

建立一套能在答辩时直接展示的量化评估体系。

### 必须回答的评委问题

1. 你的系统比之前强在哪里？
2. 你的多 Agent 到底有没有价值？
3. 你的解释为什么可信？
4. 你的失败边界是什么？

### 指标层

必须长期追踪的指标：

1. 专家失败率
2. 429 恢复成功率
3. 非法走法拦截率
4. 工具成功率
5. 无证据断言率
6. 结论降级触发率
7. 证据覆盖率
8. 前后版本回归稳定率

### 评测集层

建议至少有四类评测集：

1. 普通教学局面集
2. 高冲突复杂局面集
3. 高风险失败局面集
4. 演示稳定性场景集

### 产出

1. 评测脚本
2. 对比报表
3. 关键曲线图
4. 答辩用摘要表格

### 成功标准

1. 任何重要改动都能量化前后差异
2. 答辩时不再只能讲理念，而能讲证据

## 决策原则

后续所有改动，都应该用下面 4 个问题审视：

1. 这个改动能降低失败率吗？
2. 这个改动能提高证据可信度吗？
3. 这个改动能帮助答辩解释吗？
4. 这个改动如果今天不做，会不会阻塞主线？

如果 4 个问题里只有一个模糊的“也许会更高级”，那就不该优先做。

## 推荐执行顺序

推荐未来实施顺序如下：

1. 完成 Phase 0 剩余收口
2. 立即进入 Phase 1 动作空间约束
3. 然后推进 Phase 2 证据裁决化
4. 再开始 Phase 4 评测体系
5. Phase 3 案例知识化穿插进行
6. 最后统一收束 Phase 5 演示体验

这个顺序的理由是：

1. 没有可靠性，就没有可信度
2. 没有协议约束，就没有精确性
3. 没有评测，就没有答辩说服力
4. 没有演示收束，就没有现场完成度
