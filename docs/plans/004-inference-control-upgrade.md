# Plan: 推理时控制升级方案

## Context

当前系统在规则层、Evidence Map、工具协议、多专家协作上已经具备很好的基础，但最近暴露出的主要问题已经不再是“缺功能”，而是“推理时控制不够强”。

已经确认的症状包括：

1. 能识别到特征，但不一定抓住当前阶段最该讲的主矛盾。
2. 能检索到知识，但可能把知识套错情景，形成“知识乱用”。
3. 能生成综合讲解，但在证据不足时仍会产出看似合理的叙述。
4. 固定 CoT/固定模板在部分局面下过于僵硬，无法根据张力、阶段和分歧动态展开。

这说明系统下一阶段的关键，不是继续横向堆 prompt，而是把“分析时如何分配注意力、何时展开、何时验证、何时收缩”做成显式机制。

## 目标

本方案目标是把系统从“有工具的多专家系统”升级为“可验证、可裁决、可按情景调度的推理系统”：

1. 让关键断言默认进入验证回路，而不是直接进入成稿。
2. 让分析流程先判情景，再决定展开哪些子问题。
3. 让多候选分析的优胜判断由引擎与规则约束完成，而非模型自评。
4. 让高风险局面获得更强推理预算，低风险局面保持快速响应。

## 核心判断

### 判断 1：现阶段的主要矛盾是 inference-time control，而不是知识绝对不足

系统已经具备：

1. 规则事实抽取
2. 引擎候选与评分
3. 战术标签与张力信号
4. 相似局面检索与棋理检索

因此下一阶段最重要的是控制推理流程，而不是优先扩写更多提示词。

### 判断 2：应优先做低成本高收益改造，而不是直接引入重型研究框架

像 AGoT、rStar、reasoning MCTS 这类方法有参考价值，但短期更适合作为设计原则，而不是直接工程落地目标。

当前更适合的路线是：

1. 工具校验回路
2. 情景驱动分解
3. 引擎/标签裁判式多候选

### 判断 3：比赛窗口内最值得做的是“缩减版推理系统”，而不是完整搜索框架

近期关于 Self-Discover、ToT、PRM、DSPy 的启发是成立的，但不应直接翻译成完整的树搜索或多角色长文辩论，否则会进一步推高当前已经紧张的时延预算。

现阶段更合适的工程化原则是：

1. 不再继续扩写统一 CoT 范文，而是固化少量局面类型的“协议卡”。
2. 不再让每个新增角色都产出长文，而是引入只判错、不扩写的 verifier。
3. 不把标签当解释素材，而是把关键标签、张力和预算转成状态变量。
4. 区分演示模式与高质量模式，允许同一条链路使用不同推理预算。

## 实施方案

### 方案 1：工具校验回路

目标：把“会说”变成“会自证”。

建议流程：

1. 专家或协调器先生成草稿结论。
2. 从草稿中抽取原子断言。
3. 按断言类型规划对应工具验证动作。
4. 执行工具，生成 verification table。
5. 用验证结果重写最终讲解，删除未证实或证据不足的表述。

优先覆盖的断言类型：

1. 某子是否无根
2. 某步是否亏损/改善
3. 是否存在强制手或直接威胁
4. 当前主计划是否成立
5. 对手是否存在明确反击资源

建议接入点：

1. [core/llm/multi_agent_orchestrator.py](core/llm/multi_agent_orchestrator.py)
2. [core/llm/claim.py](core/llm/claim.py)
3. [core/llm/agent_tools.py](core/llm/agent_tools.py)

### 方案 2：情景驱动分解

目标：把固定 CoT 升级为情景驱动的分析骨架。

基本原则：

1. 先判阶段，不够。
2. 还要判情景。
3. 情景决定检查顺序、证据顺序、讲解顺序。

建议第一批情景类型：

1. 开局主线推进
2. 开局脱谱预警
3. 中局先手压制
4. 中局兑子简化
5. 中局守势反击
6. 残局优势转化
7. 残局守和求生
8. 高张力战术局面
9. 引擎近似等值多候选局面

每类情景固定输出骨架：

1. 当前情景判断
2. 主导矛盾
3. 非主焦点纠偏
4. 必查项
5. 证据顺序
6. 最终教学组织方式

建议接入点：

1. [core/llm/thinking_templates.py](core/llm/thinking_templates.py)
2. [core/llm/analysis_policy.py](core/llm/analysis_policy.py)
3. [core/llm/fewshot_examples.py](core/llm/fewshot_examples.py)

### 方案 3：引擎/标签裁判式多候选

目标：减少“漏掉关键战术”与“只看第一条 plausible line” 的问题。

建议机制：

1. 只在高风险局面生成多条候选解释或候选方案。
2. 候选之间不靠语言风格竞争，而靠外部信号评分。
3. 评分优先依据引擎 regret、标签命中率、原子断言验证通过率。

建议触发条件：

1. 引擎前两候选接近
2. 张力较高
3. 多专家结论不一致
4. 某关键工具结果与初稿冲突

建议评分指标：

1. 推荐着法与引擎 top-k 的一致度
2. 提到的关键战术点与规则标签的匹配度
3. 原子断言的验证通过率
4. token 成本与时延预算

### 方案 4：协议卡驱动的推理路由

目标：把“该怎么想”从长篇提示词改成可选择、可复用、可验证的协议。

协议卡不是示范长文，而是一个最小推理协议，至少包含：

1. 适用条件
2. 输入状态
3. 必查项
4. 禁止项
5. 输出骨架
6. 预算建议

建议第一批协议卡：

1. 开局主线推进
2. 开局脱谱预警
3. 中局高张力战术
4. 中局计划冲突
5. 残局精算
6. 教学解释

每张协议卡应明确：

1. 当前是“原则优先”还是“候选优先”
2. 是否必须调用反证检查
3. 是否必须要求引擎或规则工具参与裁决
4. 最终讲解是否允许长散文，还是应压缩成短结论

建议接入点：

1. [core/llm/analysis_policy.py](core/llm/analysis_policy.py)
2. [core/llm/thinking_templates.py](core/llm/thinking_templates.py)
3. [core/llm/multi_agent_orchestrator.py](core/llm/multi_agent_orchestrator.py)

### 方案 5：状态变量化

目标：让模型不是在“套概念”，而是在“更新局面状态”。

不建议一开始就做大状态机，先显式化少量高价值状态：

1. `initiative = strong / weak / contested`
2. `king_danger = high / medium / low`
3. `forcing_mode = on / off`
4. `plan_horizon = tactical / strategic / endgame`
5. `evaluation_stability = stable / volatile`
6. `material_stability = stable / unstable`

这些状态应来自规则标签、张力、引擎边际差和阶段检测，而不是来自模型自由生成。

建议使用方式：

1. 路由器先读状态，选择协议卡
2. 专家输出时必须引用当前状态
3. 合成器不能跨越状态直接拔高结论
4. verifier 发现“标签直接偷换成行动建议”时直接打回

### 方案 6：轻量 verifier

目标：增加一个只判错、不扩写的新环节，抑制“讲得像但不真”。

verifier 不应再是一个会生成长文的专家，而应是结构化裁判，输入是：

1. Claim 列表
2. EvidenceChain
3. 当前状态变量
4. 候选主张或最终草稿

输出建议固定为：

1. `pass`
2. `failed_claims`
3. `reason`
4. `needs_recheck_tools`
5. `counterexample_found`

verifier 首批只检查三件事：

1. 事实来源是否合法
2. 有没有把标签或棋理偷换成行动建议
3. 有没有被简单反例或引擎边际差击穿

建议接入点：

1. [core/llm/claim.py](core/llm/claim.py)
2. [core/llm/multi_agent_orchestrator.py](core/llm/multi_agent_orchestrator.py)
3. [core/llm/agent_tools.py](core/llm/agent_tools.py)

### 方案 7：快慢双模式

目标：把推理制度和时延预算绑定，避免所有问题都走最重链路。

建议两档模式：

1. 演示模式：快协议卡 + 快专家 + 快合成，优先首屏速度与稳定输出
2. 高质量模式：快专家 + 重合成 + 可选 verifier，优先讲解完整度和证据裁决

两档模式共享同一套状态变量和协议卡，但预算不同：

1. 专家数
2. 分支数
3. verifier 是否启用
4. 合成模型档位
5. 允许的最大 token 与轮次

## 分阶段落地顺序

### Phase A：先接验证回路

这是最高 ROI 的第一步，因为它直接抑制“合理但不真”的讲解。

### Phase B：再把阶段模板升级为情景模板

这是解决“抓不住重点”和“标签焦点错位”的主路径。

### Phase C：最后只在高风险局面启用多候选裁判

这样可以控制复杂度和时延，不把整套系统推成重型搜索框架。

### Phase D：引入协议卡、状态变量和快慢双模式

这是把前沿“推理结构优先”思想真正转成比赛可落地工程的关键一步。

建议落地顺序：

1. 协议卡先行
2. 状态变量最小集
3. verifier 轻量版
4. 快慢双模式

## 暂不优先的方向

以下方向保留研究参考价值，但不建议近期重投入：

1. AGoT / rStar / reasoning MCTS 的完整框架化落地
2. Soft Prompt / Prefix Tuning / P-Tuning 这类带优化环节的方法
3. DoLa / Contrastive Decoding 这类需要模型内部访问能力的方法
4. 多个会写长文的辩论角色同时上场
5. 把 RAG 用来检索具体局面答案而不是抽象原则

原因不是这些方向无价值，而是它们与当前比赛优先、闭源 API 优先、快速验证收益的目标不完全一致。

## 验证方法

验证不能只看“讲得像不像”，要看结构化指标：

1. 原子断言验证通过率是否提升
2. 关键标签 recall 是否提升
3. 高张力局面的漏检率是否下降
4. 开局/中局/残局中“偏题讲解”比例是否下降
5. 推荐着法与引擎 top-k 一致度是否提升
6. 单次分析平均时延是否仍处于可演示范围
7. verifier 打回率是否集中在“标签偷换建议”“未验证无根/受攻”“反例未覆盖”三类高风险错误
8. 演示模式下首个有效正文 chunk 是否进入可接受窗口

## 成功标准

1. 系统不再轻易把宽松结构标签误升为教学主焦点。
2. 综合讲解中的关键结论可以追溯到工具或引擎证据。
3. 不同情景下的讲解结构明显不同，而不是统一套话。
4. 只有高不确定局面才消耗额外推理预算。
5. 新机制能转化为评测指标和比赛答辩表述，而不是只增加系统复杂度。

## 最小落地清单

如果以比赛窗口为前提，建议只承诺以下最小闭环：

1. 6 张协议卡
2. 4 到 6 个核心状态变量
3. 1 个轻量 verifier
4. 1 套快慢双模式预算开关

不建议当前阶段承诺：

1. 完整树搜索
2. 多角色长文辩论
3. 大规模自动 prompt 编译系统

原因不是这些方向无价值，而是它们短期难以在时延、稳定性和答辩可解释性之间取得平衡。
