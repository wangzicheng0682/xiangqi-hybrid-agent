# Plan: 数据与知识资产建设方案

## Context

当前系统的下一阶段提升，已经不能只靠继续设计架构来完成。

仓库里已经有若干重要入口：

1. [core/llm/analysis_recorder.py](core/llm/analysis_recorder.py) 可以记录完整分析过程。
2. [core/llm/fewshot_examples.py](core/llm/fewshot_examples.py) 已有少量示范样本。
3. [core/llm/knowledge_retriever.py](core/llm/knowledge_retriever.py) 已具备棋理原则卡雏形。
4. [core/rag/position_similarity.py](core/rag/position_similarity.py) 已可使用本地样本做相似局面检索。
5. [data/training/position_data.jsonl](data/training/position_data.jsonl) 等文件已提供局面样本基础。

但这些资产仍然偏分散，尚未形成一套“能持续积累、能直接服务调教、能支持评测”的知识资产体系。

## 目标

本方案的目标不是单纯增加数据量，而是建设一套高质量、结构化、可复用的资产体系，使系统后续优化有明确抓手：

1. 失败有地方沉淀
2. 好示范有地方复用
3. 知识有适用条件和反例
4. 评测有标准题集和量化指标
5. 后续调教能依赖资产，而不是依赖临场写 prompt

## 核心判断

### 判断 1：当前最缺的是结构化高质量资产，而不是海量原始数据

对于这套系统而言：

1. 一万盘未整理棋谱，不如 200 条高质量失败案例。
2. 一本没切碎的棋书，不如 100 张带条件和反例的知识卡。
3. 一堆冗长 prompt，不如 30 条按情景组织的教学示范。

### 判断 2：资产建设必须直接服务于三件事

1. 抓重点
2. 不乱用知识
3. 可验证地提升质量

如果某类数据不能帮助以上三件事，就不应排到高优先级。

## 资产建设优先级

### 优先级 1：失败案例库

这是最高优先级资产。

要重点积累的失败类型：

1. 抓错重点
2. 知识乱用
3. 讲解空泛
4. 应调工具却未调工具
5. 已调工具但成稿未吸收证据
6. 合成器把次要结构误讲成主矛盾

每条失败案例建议字段：

1. FEN
2. 用户问题
3. 阶段与情景标签
4. 系统原输出
5. 错因分类
6. 缺失检查项
7. 正确讲法摘要
8. 是否已回归测试覆盖

数据来源：

1. 线上真实分析日志
2. [core/llm/analysis_recorder.py](core/llm/analysis_recorder.py) 输出
3. 修 bug 过程中暴露的典型场景

### 优先级 2：情景化示范库

这是后续 few-shot、scenario curriculum、情景模板的基础资产。

不要只按开局/中局/残局粗分，而要按任务情景组织：

1. 开局主线推进
2. 开局脱谱预警
3. 中局先手压制
4. 中局兑子简化
5. 中局守势反击
6. 残局优势转化
7. 残局守和韧性
8. 高张力战术局面
9. 多候选近似等值局面

每条示范建议字段：

1. 情景判断
2. 主导矛盾
3. 非主焦点纠偏
4. 必须检查项
5. 工具调用顺序
6. 证据组织顺序
7. 面向用户的最终讲法

### 优先级 3：原子断言验证映射表

这是把验证回路真正工程化的关键资产。

核心形式是：

1. 断言类型
2. 风险等级
3. 必要验证工具
4. 最低证据要求
5. 可接受的降级说法

第一批断言类型建议覆盖：

1. 子力是否无根
2. 某步是否改善/亏损
3. 是否存在强制手
4. 是否存在明确反击资源
5. 某项原则是否适用当前局面

### 优先级 4：评测题集

这是所有后续优化的硬约束基础。

每条评测题建议字段：

1. FEN
2. 用户问题
3. 阶段
4. 情景标签
5. 关键战术标签
6. 关键张力
7. 引擎基准答案
8. 可接受候选答案
9. 必须提到的点
10. 不应提到的点
11. 参考教练讲解

第一版题集不必追求很大，先做 200 到 500 条高质量样本即可。

## 第二层资产

### 资产 5：知识卡与反例卡

当前知识检索方向是对的，但应继续把知识压缩为小而硬的卡片，而不是长文本堆积。

每张知识卡建议包含：

1. 原则内容
2. 适用条件
3. 常见误用
4. 反例/例外
5. 适用阶段
6. 关联标签
7. 关联情景

优先补齐的知识类型：

1. 开局原则卡
2. 中局计划卡
3. 残局转化卡
4. 误用纠偏卡
5. 标签误导纠偏卡

### 资产 6：相似局面样本集

已有基础样本库，但后续应从“能召回”升级到“召回有教学价值”。

每条相似局面样本除了 FEN 与 best move，还应尽量补齐：

1. 核心矛盾描述
2. 参考计划
3. 结果走向
4. 为什么相似
5. 与当前局面的关键差异

### 资产 7：教学反馈与偏好数据

中长期需要建设“哪种讲法更像好教练”的反馈层。

初期可以只收集轻量反馈：

1. 是否抓住重点
2. 是否空泛
3. 是否有证据感
4. 是否有可操作建议
5. 是否适合当前水平用户

## 建设顺序

### Phase A：先建失败案例台账

所有已知 bug、已知掉价场景、线上误讲场景先统一收口。

### Phase B：把失败案例中最典型的场景升格为情景示范

也就是把“坏例子”反推出“好示范”。

### Phase C：同步沉淀断言验证映射表

让验证规则不再散落在脑中，而是进入可执行资产。

### Phase D：形成小而硬的评测题集

后续每次调 prompt、调路由、调合成器，都必须过这套题。

### Phase E：继续扩知识卡和相似局面元数据

在前四步完成之后，再扩容知识和样本，收益才更稳定。

## 验证方法

资产建设是否有效，要看这些指标：

1. 新增失败案例是否能被复现与分类
2. 典型场景是否能沉淀为可复用 few-shot 或模板
3. 每次优化后，评测题集分数是否提升
4. 知识调用后，错误套用原则的比例是否下降
5. 高张力局面的解释 recall 是否提升
6. 新增资产是否真正进入主链路，而不是只放在文档中

## 成功标准

1. 团队不再靠记忆追踪系统缺陷，而是有成体系的失败案例库。
2. 示例库不再只是演示样本，而能真正驱动情景化教学。
3. 知识库不再只是“检索到一段话”，而是能告诉系统什么时候能用、什么时候不能乱用。
4. 每次改进都能在题集和日志中看到可量化收益。
5. 资产建设能持续反哺验证回路、情景模板和比赛答辩材料。
