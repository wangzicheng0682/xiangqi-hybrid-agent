# 59M 象棋局面模型阶段性诊断报告

## A. 当前模型与数据现状

### 模型配置
| 项目 | 数值 |
|------|------|
| 参数量 | 59,605,766 (~60M) |
| 架构 | 8层 Transformer |
| Embedding 维度 | 768 |
| 注意力头 | 8 |
| 位置编码 | 可学习 1D 编码 |

### 数据配置
| 项目 | 数值 |
|------|------|
| 训练数据 | 1,000,000 局面 |
| 数据来源 | Neo4j 随机采样 + Pikafish depth 8 标注 |
| 标注内容 | state_value, action_value, best_move, semantic_tags |

### 训练配置
| 项目 | 数值 |
|------|------|
| Epochs | 10 |
| Batch Size | 32 (有效 64) |
| 学习率 | 3e-5 (Cosine 衰减) |
| 当前进度 | Epoch 9/10 |
| 损失变化 | 1.1 → 0.02 |

### 当前任务定义
**输入**：FEN 字符串 → Tokenize → 100 维整数序列
**输出**：state_value（局面分数）、action_values（动作值）、policy_logits、embedding、semantic_tags
**监督信号**：MSE Loss(state_value) + MSE Loss(action_value)
**优化目标**：让模型预测引擎对局面的评估分数

## B. 风险诊断

### 1. 数据量与模型容量严重不匹配

**问题**：60M 参数 vs 100 万样本

**理论分析**：
- 深度学习经验法则：每个参数需要 10-100 个样本
- 60M 参数至少需要 6 亿样本才能充分训练
- 当前比例：1:16（样本:参数）
- 结论：**严重欠配，但不是过拟合风险，而是欠拟合风险**

**实际表现**：
- 损失快速下降到 0.02，但这不说明学得好
- 可能只是记住了训练集的分数分布
- 泛化能力存疑

### 2. 监督信号过于简单

**问题**：只用了 state_value 和 action_value

**缺失的监督**：
- 没有 policy 监督（best_move 没用上）
- 没有 semantic 监督（标签太简单）
- 没有对比学习（相似局面应该有相似表示）

**后果**：
- 模型只学会了"猜分数"
- 没有学会"理解局面结构"
- 没有学会"识别棋理模式"

### 3. 语义标签形同虚设

**当前实现**：
```python
if piece_count >= 28:
    semantic_tags['opening'] = 0.9
elif piece_count >= 16:
    semantic_tags['middlegame'] = 0.9
else:
    semantic_tags['endgame'] = 0.9
```

**问题**：
- 这不是"语义"，这是"数数"
- 模型学不到任何棋理
- 语义头没有真正的监督信号

### 4. 缺乏验证机制

**问题**：没有验证集，没有测试集

**后果**：
- 无法判断是否过拟合
- 无法评估泛化能力
- 损失下降可能是"记住训练集"

### 5. 任务定位模糊

**核心问题**：这个模型到底要做什么？

| 选项 | 当前支持 | 问题 |
|------|----------|------|
| 直接下棋 | ❌ | 没有学 policy |
| 局面评估 | ⚠️ | 可能只是记忆 |
| 特征提取 | ⚠️ | 没有对比学习 |
| 语义输出 | ❌ | 标签太简单 |

## C. 能力定位判断

### 当前模型最适合的角色

**结论：局面表征提取器（需要后处理）**

**理由**：
1. 60M 参数的 Transformer 有足够的表示能力
2. 100 万样本足以学到基本的局面模式
3. 损失下降说明模型确实在学习

**不适合的角色**：
- ❌ 直接决策器：没有学 policy
- ❌ 语义解释器：标签太简单
- ❌ 战术计算器：没有搜索能力

### 最合理的定位

**"带分数倾向的局面向量生成器"**

输入 FEN → 输出 768 维向量 + 粗略分数

这个向量可以用于：
- 相似局面检索
- 作为下游任务的输入
- 作为更大系统的一个组件

## D. 面向"特征解析-语义编译-矛盾识别"的升级方案

### 第一阶段：验证当前模型（1-2天）

**目标**：确认模型学到了什么

**行动**：
1. 创建验证集（从 100 万中分出 10%）
2. 测试损失差异（训练集 vs 验证集）
3. 测试相似局面检索能力
4. 测试分数预测准确性

**判断标准**：
- 验证损失 < 训练损失的 1.5 倍 → 可用
- 验证损失 >> 训练损失 → 过拟合，需正则化

### 第二阶段：添加语义探测头（3-5天）

**目标**：让模型能输出有意义的语义标签

**方案**：
1. 冻结主模型
2. 设计 20-30 个语义标签（见下表）
3. 用规则/引擎生成标签
4. 只训练语义头

**语义标签设计**：

| 类别 | 标签示例 | 生成方式 |
|------|----------|----------|
| 阶段 | opening/middlegame/endgame | 规则（改进版） |
| 主动权 | red_active/black_active/balanced | 引擎评估符号 |
| 王安全 | king_safe/king_exposed/king_under_attack | 规则检测 |
| 子力 | material_even/red_ahead/black_ahead | 数子 |
| 结构 | pawn_chain/isolated_pawn/connected | 规则检测 |
| 战术 | has_check/has_threat/quiet | 规则+引擎 |

### 第三阶段：接入规则特征（1周）

**目标**：让模型输出与规则系统对齐

**方案**：
1. 实现基础规则检测器（双车、马炮配合等）
2. 将规则输出作为额外监督
3. 多任务学习：分数 + 规则匹配

### 第四阶段：语义状态生成（1-2周）

**目标**：输出结构化的语义状态

**方案**：
1. 设计语义状态 schema
2. 训练模型输出结构化 JSON
3. 与解释系统对接

### 第五阶段：矛盾识别（2-3周）

**目标**：识别局面中的核心矛盾

**方案**：
1. 收集"有矛盾"的局面标注
2. 训练分类头
3. 输出矛盾类型和位置

## E. 近期实验路线

### 实验 1：验证集泛化测试

**目的**：确认模型是否真的学到了东西

**做法**：
1. 从 100 万中随机抽取 10 万作为验证集
2. 对比训练损失和验证损失
3. 可视化损失曲线

**预期现象**：
- 验证损失接近训练损失 → 学到了通用模式
- 验证损失明显高于 → 过拟合

### 实验 2：相似局面检索测试

**目的**：测试 embedding 质量

**做法**：
1. 取 1000 个测试局面
2. 用模型生成 embedding
3. 计算余弦相似度
4. 人工检查最相似的 5 个局面是否"真的相似"

**预期现象**：
- 相似局面 embedding 相似 → 可用于检索
- 随机结果 → embedding 没学到结构

### 实验 3：打乱标签对照实验

**目的**：确认模型不是在学伪规律

**做法**：
1. 随机打乱 10% 的标签
2. 重新训练
3. 对比损失下降速度

**预期现象**：
- 打乱后损失下降慢 → 模型确实在学习
- 打乱后损失一样快 → 模型在学伪规律

### 实验 4：语义头探测实验

**目的**：测试模型内部是否有棋理知识

**做法**：
1. 冻结主模型
2. 用规则生成语义标签
3. 只训练语义头（线性层）
4. 测试准确率

**预期现象**：
- 准确率 > 70% → 模型内部有棋理知识
- 准确率 ≈ 随机 → 模型没学到棋理

### 实验 5：分数预测校准测试

**目的**：测试分数预测是否可靠

**做法**：
1. 用引擎重新分析 1000 个测试局面（depth 12）
2. 对比模型预测 vs 引擎真实分数
3. 计算 MAE 和相关系数

**预期现象**：
- MAE < 0.5（50分）→ 可用
- MAE > 1.0 → 不可靠

## G. 如果不追求"下得强"，先追求"讲得对"

### 核心思路

**从"直接预测"转向"中间语义提取"**

当前模型的问题是：它被训练成一个"黑箱分数预测器"。但如果我们改变训练目标，它可以成为一个"语义特征提取器"。

### 改造方案

#### Step 1：重新定义输出

不再预测"分数"，而是预测"状态"：

```
输入：FEN
输出：
  - 阶段标签（opening/middlegame/endgame）
  - 主动权标签（red/black/balanced）
  - 结构标签（开放/封闭/半开放）
  - 战术标签（有杀棋/有战术/平稳）
  - 风险标签（红方危险/黑方危险/均势）
```

#### Step 2：设计标签生成器

```python
class SemanticLabelGenerator:
    def generate(self, fen: str, engine_analysis: dict) -> dict:
        labels = {}
        
        # 阶段（改进版）
        labels['phase'] = self._detect_phase(fen)
        
        # 主动权
        score = engine_analysis['score']
        labels['initiative'] = 'red' if score > 30 else 'black' if score < -30 else 'balanced'
        
        # 结构
        labels['structure'] = self._detect_structure(fen)
        
        # 战术
        labels['tactics'] = self._detect_tactics(fen, engine_analysis)
        
        # 风险
        labels['risk'] = self._detect_risk(fen, engine_analysis)
        
        return labels
```

#### Step 3：重新训练

1. 用引擎重新标注 100 万局面（这次生成丰富标签）
2. 修改损失函数：多标签分类损失
3. 训练语义头

### 这样改造的好处

1. **可解释**：输出的是人类可理解的标签
2. **可验证**：可以人工检查标签是否正确
3. **可用**：可以直接接入解释系统
4. **可扩展**：后续可以增加更多标签

### 在大系统中的位置

```
Position Encoder (改造后)
        ↓
    语义标签输出
        ↓
    ┌──────────────┐
    ↓              ↓
解释系统        决策系统
(直接用)       (作为特征)
```
