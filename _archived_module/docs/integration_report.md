### 2.3 方法论反思：关于"语义探测"的修正

**原报告措辞（错误）**：
> "语义探测93.3%准确率，证明模型内部有棋理知识"

**修正后的表述**：
> 当前实验验证了模型表示对"阶段"标签具有较强可分性，但由于该标签与表层局面统计高度相关，且模型训练中已包含语义监督，因此该结果不能被解释为"模型已形成深层棋理知识"。

**问题分析**：

| 问题 | 说明 |
|------|------|
| 不是严格意义上的probe | 模型训练时已带有semantic_head学习语义标签，这是训练目标验收，不是独立探测 |
| 任务本身太容易 | "开局/中局/残局"主要由子力数量规则生成，与FEN表层统计高度耦合 |
| 过度外推 | 从"phase分类93.3%"跳到"模型有棋理知识"，缺少中间证据链 |

**更严格的实验应包含**：
1. 冻结不带语义监督训练过的backbone，再单独probe
2. 避开表层可直接读出的标签，测试更难的语义判断
3. 做强基线对照（手工统计特征、浅层MLP等）
4. 做分布外验证

**结论**：该实验应定位为"语义层可观测性验证"，不是"棋理理解证明"。

## 三、语义状态生成器 v1

### 3.1 设计目标

将模型输出从"探针可读"变为"系统可用"：
- 每个字段标明来源（规则/引擎/模型/融合）
- 输出置信度
- 可被后续模块直接消费

### 3.2 输出字段

| 字段 | 说明 | 来源 |
|------|------|------|
| phase | 阶段（开局/中局/残局） | [RULE] 或 [MODEL] |
| initiative | 主动权归属 | [ENGINE] 或 [MODEL] |
| red_king_safety | 红方将帅安全 | [RULE] + [ENGINE] |
| black_king_safety | 黑方将帅安全 | [RULE] + [ENGINE] |
| red_coordination | 红方子力协调 | [RULE] |
| black_coordination | 黑方子力协调 | [RULE] |
| long_term_weaknesses | 长期弱点 | [RULE] + [ENGINE] |
| move_type | 着法类型 | [ENGINE] 或 [MODEL] |

### 3.3 输出示例

## 四、核心矛盾识别器 v1

### 4.1 矛盾类型体系

| 类型 | 编号 | 描述 | 最低证据要求 |
|------|------|------|--------------|
| 中路争夺 | C01 | 双方争夺中路控制 | 规则 |
| 王安全 | C02 | 将/帅安全受威胁 | **引擎必须** |
| 子力协调 | C03 | 子力配合问题 | 规则 |
| 结构弱点 | C04 | 兵/卒结构问题 | 规则 |
| 优势转换 | C05 | 需要转换优势 | **引擎必须** |
| 抢先手 | C06 | 争夺主动权 | 推断 |

### 4.2 裁决逻辑

主次矛盾裁决基于以下原则：

1. **解释引擎首选着** (+40分)
2. **统一最多语义标签** (+30分)
3. **影响后续变化** (+20分)
4. **证据强度** (+10-30分)
