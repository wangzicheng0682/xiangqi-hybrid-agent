Xiangqi Hybrid LLM-Agent Analysis System   核心技术栈深度研究报告

1.项目概述与背景

Xiangqi    Hybrid    LLM-Agent    Analysis     System 是一个开源的中国象棋智能 分析、对弈与讲解系统，其核心目标是结合符号系统的高精度计算与大语言模 型的智能讲解，打造超越纯LLM的棋局分析能力。该项目由中国象棋引擎

Pikafish   提供零漏算的战术计算，由大模型 (DeepSeek/Qwen     系列)结合知

识图谱、经典棋书检索和视觉感知，提供人类大师级的自然语言讲解，实现 “引擎算得准+AI讲得通”的融合效果。

这一系统被视为神经符号AI(Neuro-Symbolic            AI)  在战略博弈领域的垂直  落地实践。它以LLM 作为智能代理的“大脑”,负责协调调用各类工具(符号 引擎、知识库、视觉模型等),从而在保留深度学习模型灵活性和解释力的同 时，克服其幻觉和知识局限。项目最终产品形态为开源GitHub 项目、

Gradio/Web  界面，可用于学术研究、教学辅导和对弈娱乐，其长期愿景是成 为象棋领域的“Claude” 级智能助手。

2.核心组件与技术选型

2.1象棋引擎：Pikafish

UCI+NeuralN etworkUniversallnterf ace

Pikafish    是项目战术计算的核心引擎，它是当前中国象棋领域棋力最强的开源 引擎之一。作为Stockfish 的衍生版本， Pikafish 同样遵循 UCI(Universal

Chess        Interface)  协议。UCI  是一种通用的引擎通信协议，允许引擎与图形 界面或代理程序通过标准命令交互。这意味着Pikafish    本身不包含图形界

面，需要通过 UCI  命令控制。

技术要点：

· UCI 协议通信： 项目通过Python 脚本以子进程方式启动Pikafish, 并 通过标准输入/输出与其进行 UCI 命令交互。例如，发送 uci 命令初始 化引擎， isready     确认引擎就绪， position      fen      ...  设置棋局，以 及 go depth 20 发起深度搜索等。引擎会返回最佳走法和评估得分等  信息。

● 战术精确性： Pikafish 利用神经网络评估 (NNUE  技术)和强大搜索算 法，能在复杂局面下计算出零漏算的精确着法。其计算深度通常设定在  20-30层，以保证对战略态势的准确判断。

● 集成方式： 在 LangGraph   代理中，Pikafish 被封装为 Tool1,  即一个 可被调用的工具。当LLM  需要获取战术信息时，会通过ReAct/Plan-

and-Execute     等策略调用此工具，将当前棋局 (FEN  格式)传递给引 擎，并读取引擎输出的评估结果。

2.2知识存储：知识图谱与书籍向量库

为了提供战略层面的洞察和可追溯的知识引用，系统引入了两类知识库：历史 棋局知识图谱和经典棋书向量库。

知识图谱 GraphRAG:      基于Neo4j   构建的中国象棋知识图谱，用于存储历史 对局数据、开局定式和胜率统计等信息。该图谱以棋局局面为节点，走法为

边，每个局面节点可关联该局面的胜率、出现次数、所属开局类型等属性。通 过图查询，代理可以检索相似局面或特定开局的历史数据，为用户提供“此局 面历史上红方胜率约60%”之类的统计信息，或查找相似局面的走法参考。

经典棋书RAG     BooksRAG:  利用向量数据库(如FAISS/Chroma)       存储经典 象棋书籍内容的向量表示。这些书籍包括《橘中秘》《梅花谱》《象棋实用残

局》等经典著作，以及《象棋攻防妙法》《象棋中局战法》《象棋布局原理》等 现代名著。通过PDF  文档切分和嵌入向量，构建起棋书内容检索器。当LLM  需要战略解释或经典注解时，可以调用此检索器 (Tool3)      从向量库中获取相 关段落的原文。这些内容将作为LLM  的上下文，使其讲解能够引用大师的原 文观点，提高权威性和可信度。

技术要点：

· Neo4j 与图谱构建： 使用Neo4j 作为知识图谱的存储引擎。通过图查询 语言 Cypher    可以方便地查询“给定局面，历史上黑方最常见的应对” 或“某开局序列的胜率分布”等问题。知识图谱的构建需要导入大量

PGN  对局数据(如悟空象棋数据集、精英对局数据库等),通过解析  PGN  提取局面和结果，构建“局面-走法-结果”三元组，从而形成丰富 的开局和局面知识网络。

· 向量数据库与RAG:    采 用LangChain     的 PDFLoader     加载棋书PDF,

并使用 RecursiveCharacterTextSplitter             进行文本切分。切分后的文本 片段通过嵌入模型转换为向量，存入向量数据库。查询时， LLM  生成的 查询文本也转换为向量，在向量库中检索最相似的片段。检索结果经过

文档相关性评分后，返回给LLM 作为“外部知识”。这种检索增强生成 (RAG)   方式，确保LLM 的讲解有据可依，避免凭空杜撰。

● 优先引用权威：系统设计遵循 “Grounded-first”       原则，即讲解必须引 用知识图谱或书籍或视觉解析，不能纯靠 LLM 编造。例如，当解释某开 局策略时，LLM 会优先检索《梅花谱》中的相关论述作为依据，从而让 讲解内容更具说服力。

2.3 LLM核心：DeepSeek  API&Qwen-VL系列

大语言模型是整个系统的“大脑”,负责统筹各工具、生成讲解和与用户交 互。本项目优先采用 DeepSeek     API 提供的大模型服务，包括其对话模型

(deepseek-chat)        和推理增强模型 (deepseek-reasoner) 。DeepSeek             模 型以其在中文理解和复杂推理方面的出色表现，能够胜任棋局讲解中的多步推 理和知识融合任务。

同时，系统引入了视觉语言模型Qwen2.5-VL  系列，作为“视觉感知”模

块。Qwen2.5-VL  是阿里通义千问团队推出的开源多模态模型，具备强大的图 像理解和文档解析能力。它能处理图像、文本、视频等多种输入，并输出文本 或定位框等形式的结果。在本系统中，Qwen-VL  被用于棋盘图像理解：当输  入为棋盘图片或截图时，它能识别棋盘布局、棋子位置，并生成对局面的视觉 描述。这为LLM 提供了“看棋盘”的能力，使其讲解能够结合视觉观察到的 态势，例如“红方底线车马炮三子归边，形成强大攻势”。

技术要点：

· DeepSeek    模型调用：DeepSeek    提供了与OpenAI   兼容的API 接口。 项目通过 Python   客户端调用DeepSeek      API, 设置系统提示和用户提  示，以获取模型响应。在 LangGraph    框架中，DeepSeek    可作为对话  生成模块，根据当前状态(包括引擎结果、知识库检索结果、视觉模型  输出)生成自然语言讲解。

· Qwen-VL  视觉模型：Qwen2.5-VL   支持动态分辨率和多模态输入。它 不仅能识别常见物体，还能理解图像中的布局和结构。对于中国象棋棋  盘，它能识别出棋盘是9×10的网格、楚河汉界的位置，以及每个交叉点 的棋子。通过将棋盘图像输入Qwen-VL,    模型可以生成结构化的描述，

例如棋子的位置、红黑双方的势态等。这种描述将作为 LLM 的输入，帮 助其从视觉层面理解局面。

·DeepSeek         vs         Qwen-VL:DeepSeek 侧重于文本理解和生成，是讲解 输出的主力模型；而Qwen-VL  则是视觉感知的前置模型，为DeepSeek 提供额外的视觉上下文。两者协同工作，使系统既能“算得准”

(Pikafish),  又能“看得清” (Qwen-VL),    还能“讲得通” (DeepSeek)。

2.4 Agent框架：LangGraph Orchestrator

LangGraph  是项目采用的Agent 框架，用于构建和管理 LLM  驱动的智能代 理。它是LangChain    生态的一部分，提供了一个图结构来定义代理的行为流 程。与传统基于链式提示的Agent  不 同 ，LangGraph    允许开发者以状态机的 方式设计代理，包括多个节点 (Node)  和边 (Edge),   从而实现复杂的决策 逻辑和工具调用策略。

架构设计：本系统初步采用ReAct   Reason    +Act  风格的代理架构。ReAct  是 一种让LLM 通过自我提示 (self-prompting)        进行思考-行动循环的模式。

LangGraph  将这一模式具象化为一个图：

● 节 点 (Nodes):    图中的节点代表代理的不同状态或功能模块。例如，

一个节点负责调用Pikafish 工具，另一个节点负责检索知识图谱，还有  节点负责调用Qwen-VL  模型等。每个节点执行特定任务后，会将结果写 入代理的共享状态 (Memory)。

● 边 (Edges):   边定义了节点之间的流转逻辑。边可以是简单的顺序执  行，也可以是条件分支。例如，一个条件边可以判断“是否已有引擎评  估结果”,如果没有，则转向调用引擎的节点；如果有，则转向调用知  识库检索的节点。LangGraph    支持条件边，使代理能根据当前状态选择 下一步动作。

运行流程：当用户输入一个棋局 (FEN 或图片)后， LangGraph    代理从起始 节点开始执行。例如，起始节点可能是预处理：判断输入类型，如果是图片则 先调用视觉模型提取棋盘信息；如果是文本FEN则直接进入下一步。接着，代 理进入引擎计算节点，调用Pikafish 获取最佳着法和评估。随后，代理进入  知识检索节点，根据当前局面查询知识图谱或棋书向量库，获取相关的历史统

计或大师观点。最后，代理进入讲解生成节点，将所有收集到的信息(引擎结 果、知识库结果、视觉描述)作为上下文，由 DeepSeek    模型生成最终的自然 语言讲解。

技术要点：

● 状态管理： LangGraph   使用一个全局状态对象(通常是一个字典)来 存储代理在执行过程中的所有中间结果。例如，状态中可包含

“engine_result” 、“kg      result” 、“book_result”、

“visual_desc”      等字段。各节点通过读写这个状态来协同工作。

· ReAct   模式实现： 在 LangGraph     中，可以通过设计节点和边来实现 ReAct  的推理循环。例如， 一个节点生成一个内部提示 (thought),

下一个节点根据这个提示选择工具 (action),         再下一个节点处理工具  的输出 (observation)。  这种思考-行动-观察的过程可以循环多次，直 到代理认为信息充分，可以生成最终答案。

· 灵活扩展： LangGraph     的图结构使得添加新工具或新流程变得容易。 例如，如果将来引入新的分析工具(如残局求解器),只需在图中增加 相应节点和边即可，无需重写整个代理逻辑。这符合项目“固定架构、 支持迭代”的原则。

2.5用户界面与交互：Gradio/Streamlit

用户界面是系统与用户交互的窗口。在MVP  阶段，项目选用Gradio 作为前 端工具。Gradio    是一个 Python    库，可以快速构建机器学习模型的演示界

面，支持文本、图像等多种输入输出类型。通过 Gradio, 开发者可以用少量 代码搭建一个Web  界面，让用户输入棋局(文本FEN 或上传棋盘图片),并 实时查看系统生成的分析和讲解。

界面设计： MVP  阶段的Gradio    界面将包含以下主要元素：

●输入区： 一个文本框供用户粘贴FEN 串，以及一个文件上传组件供用户 上传棋盘图片。用户可以选择任一方式输入棋局。

●输出区：分为两部分。 一是棋盘可视化：根据输入的FEN 或图片解析结 果，动态生成棋盘图像。二是讲解文本区：显示系统生成的讲解内容，

包括最佳着法、评估分析、历史数据和引用的经典论述等。

● 交互按钮： 例如“分析”按钮，点击后触发代理执行分析流程，并在界 面上更新输出结果。

技术要点：

● FEN 解析与棋盘生成： 当用户输入文本FEN 时，系统需要解析 FEN 并 生成对应的棋盘图像。这可以通过 Python 的绘图库(如 Pillow) 实

现，根据FEN  字符串绘制棋盘和棋子。已有开源项目实现了从 FEN  生 成棋盘图的功能。对于图片输入，可以先使用视觉模型提取FEN,  再 进 行相同的绘制流程。

● Gradio 集成： Gradio 提供了简单的API 来定义界面布局和回调函数。 例如，使用 gr.inputs.Textbox  和 gr.inputs.Image  定义输入，使 用 gr.outputs.Image  和 gr.outputs.Textbox  定义输出。在回调函 数中，实现从输入到输出的处理逻辑，即调用后端的Agent  获取结果。

● 后续扩展： 在 MVP  验证成功后，界面可升级为更复杂的Streamlit 或  自定义Web 应用，以支持更多功能(如对弈模式、实时讲解等)。但无 论如何演进，界面都将严格遵循本规划，作为“用户导向”的窗口，确  保讲解内容对人类棋手友好、易懂。

3.系统工作流程

综合以上组件，系统的典型工作流程如下：

1. 用户输入棋局： 用户通过Gradio   界面输入棋局信息，可以是文本形式 的 FEN,    或上传一张棋盘截图/照片。

2.输入预处理：后端首先判断输入类型。如果是图片，则调用Qwen-VL

模型进行棋盘识别，生成棋局的FEN 和对局势的初步视觉描述。如果是 文本 FEN,   则直接进入下一步。

3.引擎战术分析： 后端通过 UCI 协议将棋局 FEN 发送给 Pikafish 引擎， 要求其计算最佳着法和局面评估(例如“红方胜率65%”)。引擎返回 的结果(如最佳走法“炮二平五”,胜率评估)被存入代理状态。

4.知识检索增强： 后端根据当前局面，在知识图谱中检索相似局面的历史 胜率和常见走法，以及在棋书向量库中检索相关经典论述。例如，知识 图谱可能返回“此局面历史上红方胜率60%,黑方常见应对是马2进

3”,棋书向量库可能返回《橘中秘》中关于该开局的一段注解。这些检 索结果同样存入代理状态。

5.多模态信息融合： 后端将步骤2得到的视觉描述、步骤3得到的引擎结

果、步骤4得到的知识结果汇总。这些信息共同构成了LLM  生成讲解的 上下文。

6.LLM  讲解生成： 后端调用DeepSeek  模型，将上述所有上下文信息整 合进提示词，让模型生成自然语言的讲解。提示词会强调“首先给出最 佳着法，然后结合视觉观察和历史数据进行分析，最后引用权威观

点”。DeepSeek    模型据此生成一段解释，例如：“红方最佳着法是炮 二平五(炮二平五),此着法历史上红方胜率约60%【知识图谱】。当 前局面红方底线车马炮三子归边，形成强大攻势【视觉模型】。正如

《橘中秘》所言： ‘当头炮势如破竹’,红方应抓住时机迅速突破【棋 书RAG】。”

7.结果输出：后端将生成的讲解文本返回给前端界面，在输出区显示。同 时，如果输入是文本 FEN,   后端会生成对应的棋盘图像；如果是图片输 入，则可能直接显示用户上传的图片(或由系统绘制的棋盘图)。这

样，用户既看到可视化的棋盘，又读到图文并茂的讲解。

这一流程确保了工具优先(先引擎计算，再知识检索，最后LLM 生成)和知识 引用优先 (讲解内容有据可查)的原则得到贯彻。通过 LangGraph  的状态管 理和流程控制，各组件协同工作，实现了“输入棋局 → 多工具分析 →LLM 综 合讲解”的完整闭环。

4.设计原则与迭代策略

本项目在设计和开发过程中，严格遵循一系列设计原则，并采用敏捷迭代的方 法逐步完善系统。

核心设计原则：

● Tool-first (工具优先):任何精确计算和事实查询，都必须先通过专用 工具完成，再由 LLM 处理。这意味着引擎计算胜率、知识图谱查统计、 书籍查原文等，都不依赖LLM 的幻觉，而是由可靠工具提供。LLM 的  职责是基于这些工具结果进行推理和表达。

● Grounded-first (知识引用优先):讲解内容必须“有根有据”,引用 知识图谱或书籍或视觉解析的结果。避免LLM 凭空杜撰棋理或数据。例 如，不会说“历史上红方胜率很高”,而是引用具体胜率数字；不会说  “经典棋书有云…”,而是检索到具体原文再引用。

● 视觉优先： 对于复杂局面，优先生成棋盘图像并让视觉模型解析。视觉 信息能帮助LLM 更准确地理解局面结构，减少因文本FEN 描述不清导致 的误解。视觉描述将作为讲解的重要基础输入。

· 一致性： 在术语使用、数据处理上保持一致。例如，统一使用“红方/黑 方”指代，统一胜率显示格式，统一棋子符号(红方用大写字母

K/A/E/R/C/H/P,    黑方用小写)。这种一致性确保不同模块输出的信息

在人类看来是连贯的。

● 开源友好： 所有代码和模型选择都考虑可本地运行。API key等通过环 境变量配置，不影响开源发布。这保证项目成果可以被社区自由使用和 改 进 。

● 用户导向： 最终讲解以“人类棋手能看懂、能学到”为最高目标。语言

风格力求生动直观，避免过于技术化。例如，会解释为什么某步是好  棋，而不是简单给出一个胜率数字。视觉描述也会尽量贴近棋手视角， 如"红方左翼空虚，黑方可以趁机…",让用户有身临其境之感。

迭代与演进机制：

本规划文档作为“活文档 (Living  Constitution)”,会随着项目进展不断演 进。项目采用敏捷迭代模式，将整体路线划分为若干阶段 (Phase),        每个阶 段又细分为若干 Sprint    (迭代周期，约2-4周)。每个Sprint    都有明确的迭代 目标和可交付成果，例如“实现 FEN 解析和引擎调用”、“完成知识图谱基  础搭建”等。迭代流程包括：

· MVP  构建： 第一阶段 (Phase1)      专注于构建最小可行产品 (MVP),

6.神经符号增强与演绎推理能力升级

本节阐述如何通过引入神经符号混合系统的最新方法，来显著增强现有架构的分析思维与演绎推理能力。

6.1 核心技术增强方案

6.1.1 假设演绎推理引擎

原理：将LLM擅长的"假设验证"能力制度化。不再让系统直接输出最终解释，而是强制其生成若干待验证的假设，并利用引擎、知识库等外部工具进行严格的符号化演绎证明。

系统实现：
1. 节点增强：在 semantic_extractor 节点中，不仅生成语义标签，还需基于当前 semantic_state 提炼出2-3个核心假设，存入 reasoning.candidate_hypotheses。例如，若检测到 king_safety_black: fragile，则生成假设H1："黑方王翼存在可利用的结构性弱点"。
2. 验证流程：在 evidence_verifier 节点中实现 DeductiveVerifier 类：
   - 前提提取：从 semantic_state 和 facts 中提取相关前提
   - 规则匹配：在棋理概念本体中匹配相应的因果或推断规则
   - 证据绑定：每一步推导都必须绑定到具体证据（ENGINE/BOOK/KG）
   - 结论裁决：结果标记为 VERIFIED, PARTIALLY_VERIFIED, REFUTED 或 UNCERTAIN

6.1.2 思维树（Tree of Thought）规划器

原理：为解决线性推理易"一条道走到黑"的问题，引入树形搜索策略。系统可探索多种不同的战略解释路径，并利用客观工具作为评估函数，剪枝掉逻辑薄弱的分支。

系统实现：
1. 分支生成：claim_planner 根据不同的核心矛盾识别结果，生成多条解释主线
2. 分支评估：评估分数由以下因子加权计算：
   - Engine_Score_Consistency：解释与引擎评分方向的一致性
   - KG_Support_Rate：解释中关键论断在知识图谱中的历史支持率
   - Rule_Application_Count：成功应用的棋理规则数量
3. 最优路径选择：选择评估分数最高的分支进入最终的 teaching_rewriter 节点

6.1.3 面向推理的对抗验证闭环

原理：借鉴对抗生成思想，自动化地发现和修复系统推理中的逻辑漏洞。

系统实现：
1. 对抗样本生成：使用独立LLM实例作为"对手"，在关键逻辑节点引入错误
2. 系统自检：记录 evidence_verifier 成功检测出逻辑谬误的比率
3. 错误归因与修复：对于未被检测出的谬误，反馈修复 Prompt模板/棋理本体/验证器逻辑

6.1.4 语义空间映射与思维链绑定

原理：强化高层战略概念与底层具体事实的绑定关系。

系统实现：
1. 特征提取器对齐：Transformer Key Feature Extractor 输出包含空间坐标或棋子标识
2. Prompt管线强制绑定：在输出每个抽象判断后，必须用括号注明其底层依据

示例输出："红方掌握了主动权优势（依据：ENGINE评分+0.5，且PV显示连续三步先手；VISION识别红方双车炮已占开放线）。"
